# 审辩式思维动态测评系统需求规格说明书

## 1. 文档目标

本文档用于需求分析阶段，目标是明确审辩式思维动态测评系统的业务目标、系统边界、用户需求、数据需求、功能需求、性能需求和安全需求，为后续概要设计、详细设计、数据库设计和接口设计提供依据。

本阶段重点回答以下问题：

1. 系统面向哪些用户，解决哪些测评问题；
2. 系统需要支持哪些核心业务流程；
3. 系统需要采集、生成、存储和导出哪些数据；
4. AI 能力在测评流程中承担什么角色；
5. 系统边界内外分别包含哪些内容；
6. 第一版 MVP 的功能优先级和非功能要求是什么。

## 2. 项目定位

本系统定位为面向审辩式思维能力评估的智能化动态测评工具。系统以管理决策情境为载体，通过交互式背景采集、情境化任务呈现、开放式作答、多轮追问、行为证据识别、AI 可解释评分和反馈报告生成，评估用户在复杂情境中的审辩式思维表现。

系统关注的测评对象不是用户的最终选择本身，而是用户在复杂问题中如何界定问题、评估证据、组织推理、理解多方视角、整合行动方案，并在新信息出现时调整判断。

系统需要体现心理测评与人工智能技术的结合：

1. 心理测评侧提供测量构念、维度定义、评分标准、行为证据要求、信效度验证思路；
2. AI 技术侧提供交互式访谈、上下文理解、候选追问生成、证据抽取、结构化评分和报告生成；
3. 软件系统侧负责流程控制、数据留痕、配置管理、版本追踪、权限控制和数据导出。

### 2.1 专业设计原则

本系统的需求分析需要同时遵循心理测评和 AI 系统设计两类原则。心理测评侧参考教育与心理测验领域关于效度、信度、公平性、标准化施测、评分解释和测验安全的通用要求；AI 侧强调 Agent 工作流的可控性、可追溯性和输出质量控制。

1. 构念先行：系统需要先明确“审辩式思维”这一测量构念及六个维度的定义，再设计情境、追问和评分流程。
2. 证据中心：系统不直接测量抽象能力本身，而是通过情境任务诱发可观察的语言行为证据，并基于证据进行评分。
3. 标准化与适应性并存：系统允许根据用户画像适配情境表达，但核心施测流程、主测维度、评分标准和追问上限需要保持可控，避免个性化破坏结果可比性。
4. 可解释评分：每个维度的分数必须能够回溯到用户原话、行为证据、评分标准和 AI 判断理由。
5. 信效度验证：系统需要支持内容效度审查、专家评分一致性、AI 与人工评分一致性、外部效标关联和异常样本分析。
6. 公平性与伦理边界：系统需要减少与审辩式思维无关的背景差异对结果的影响，避免把报告用于高风险选拔或诊断决策。
7. AI 可控：Agent 的角色、输入、输出格式、提示词版本、专业知识上下文和失败处理机制都需要被记录和管理。

### 2.2 需求评审依据

本需求文档主要依据以下资料和原则形成：

1. 教育与心理测验领域关于效度、信度/测量精度、公平性、标准化施测、评分报告和测验安全的通用要求；
2. 审辩式思维六维能力模型、BARS/rubric、情境脚本和 CCTST 外部效标接入方案；
3. 对话式测评、Critical Questions Generation、AI 访谈、可解释对话特征评分和 LLM 自动评分等相关论文；
4. 评分缺口识别、论证漏洞识别、候选追问生成和 Follow-up Judge 筛选等 AI 追问机制设计思路。

## 3. 系统边界

### 3.1 系统范围内

系统第一版需要覆盖以下能力：

1. 前台测评端：支持测评用户进入系统、完成知情同意、进行交互式背景采集、完成情境对话、查看反馈报告、提交体验反馈。
2. AI 测评流程：支持用户画像生成、情境适配、初评分、评分缺口识别、论证漏洞识别、候选追问生成、Follow-up Judge 筛选、最终评分和报告生成。
3. 后台管理端：支持管理员维护测评情境、阶段主问题、rubric、追问策略、提示词、专业知识上下文和报告模板。
4. 数据管理：支持完整保存用户原始作答、AI 中间判断、追问过程、评分结果、证据句、报告快照和用户反馈。
5. 外部效标接入：支持导入 CCTST 等外部效标数据，并通过匿名用户编号与系统测评数据对应。
6. 质量验证支持：支持保存专家评分、AI 评分一致性、追问前后置信度变化、外部效标关联等验证数据。
7. 数据导出：支持导出后续分析所需的结构化数据。

### 3.2 系统范围外

第一版暂不覆盖以下内容：

1. 不训练或微调自有大模型；
2. 不建设复杂专家案例库或完整 RAG 知识库；
3. 不实现大规模多智能体辩论式追问；
4. 不实现复杂组织级权限体系；
5. 不直接内置 CCTST 官方测验题目；
6. 不建立正式常模、百分位解释或高风险选拔标准；
7. 不将系统评分作为唯一能力判定标准；
8. 不将测评报告用于临床诊断、招聘录用、升学选拔等高风险决策。

## 5. 核心业务需求

### 5.1 测评构念与测评蓝图

本节一句话：先说清楚系统到底测什么能力，再把这个能力拆成可观察、可评分、可配置的结构。

本系统的核心测评对象是“审辩式思维能力”。从心理测评角度看，这一节对应的是系统的能力模型设计：先定义要测量的心理能力，再把它拆解为若干可观察的维度，最后说明这些维度如何落到具体情境、问题、追问和评分标准中。

本系统将审辩式思维能力操作化为六个维度：问题界定、证据评估、推理论证、多元视角、整合决策和动态调整。

每个维度至少需要维护以下内容：

1. 维度定义：说明该维度测量什么能力；
2. 可观察行为：说明用户在对话中出现哪些语言行为可以作为该维度证据；
3. 低、中、高水平表现：对应 BARS/rubric 的分数锚点；
4. 典型证据句：用于帮助 AI 和人工评分者识别行为证据；
5. 反例或无效证据：说明哪些表达不能作为高分证据；
6. 适用情境阶段：说明该维度主要在哪些情境阶段被观察。

系统需要支持测评蓝图配置，明确每个情境阶段的主测维度、辅助观察维度、主问题、关键评分证据点和预期触发的追问方向。测评蓝图用于保证情境任务、追问机制和评分标准围绕同一测量目标展开。

预期效果：团队能够形成一套统一的“能力模型说明书”。心理测评相关成员可以据此设计维度定义、行为证据和评分标准；开发成员可以据此设计后台配置、评分数据结构和 Agent 输入输出；后续情境脚本、追问策略和报告解释都能回到同一套能力模型上。

### 5.2 交互式背景采集

本节一句话：用对话方式了解用户背景，为后续情境适配和报告解释提供上下文。

系统需要通过简短对话采集用户背景信息，而不是仅依赖静态表单。背景采集结果需要同时保存原始对话和结构化用户画像。

用户画像至少包括：

1. 用户类型：大学生、研究生、在职人员、其他；
2. 学习或工作状态；
3. 专业、行业或主要经历；
4. 项目经历、组织经历、实习或工作经历；
5. 适合的情境类型；
6. AI 画像置信度。

用户画像用于情境适配、对话上下文补充、报告解释和后续数据分析。

预期效果：用户进入测评时不会像填写普通问卷，而是通过自然对话完成背景采集。系统能够生成结构化用户画像，用于选择更合适的情境表达、补充 AI 对话上下文，并支持后续按用户类型进行数据分析。

### 5.3 情境化测评

系统需要以管理决策情境作为测评载体。第一版优先支持一个核心情境：“产品上线前 48 小时”。

本节一句话：情境不是一段静态材料，而是一组可推进、可追问、可更新信息的管理决策任务，用于观察用户在复杂信息下的判断过程。

情境需要包含：

1. 情境背景；
2. 用户角色；
3. 阶段主问题；
4. 主测维度；
5. 关键评分证据点；
6. 可适配的用户画像范围；
7. 动态信息更新节点；
8. 挑战性或陷阱性追问触发方向；
9. 情境版本号。

情境阶段应支持逐步释放信息，例如用户反馈变化、上线风险暴露、团队资源约束、市场或竞品变化、上级决策压力等。动态信息更新用于观察用户能否在新证据出现后修正判断、调整方案或重新权衡风险。

情境配置只定义测评任务和证据观察方向，不预设用户一定会出现哪些缺口。

预期效果：测评过程更接近真实管理决策，而不是静态题目作答。用户需要在不断推进的情境中理解问题、处理证据、回应约束和调整判断，系统也能通过阶段化任务采集更丰富的行为证据。

### 5.4 AI 追问机制

系统需要支持审辩式追问，而不是泛泛补充型追问。第一版追问机制采用“评分缺口驱动 + 论证模式生成 + Follow-up Judge 筛选”的流程。

本节一句话：AI 追问的目标是补充评分所需的行为证据，并检验用户能否面对质疑、约束和新信息继续保持清晰推理。

追问类型至少包括：

| 追问类型 | 作用 | 示例方向 |
| --- | --- | --- |
| 开放性追问 | 引导用户补充理由、证据或备选方案 | “你判断优先上线的关键依据是什么？” |
| 挑战性追问 | 对用户结论提出反例、冲突信息或利益相关方质疑 | “如果客服团队认为风险不可控，你会如何回应？” |
| 陷阱性追问 | 检测用户是否忽视关键约束、因果混淆、证据不足或过度自信 | “既然已有部分用户反馈积极，是否可以直接忽略测试异常？” |
| 动态信息追问 | 在对话中补充新事实，观察用户是否调整判断 | “刚收到消息，核心功能在灰度环境中出现高频报错，你会如何调整方案？” |

核心步骤包括：

1. Scoring LLM 对当前回答进行初评分，输出维度分、证据句和置信度；
2. Gap Detector 识别评分缺口；
3. Argument Issue Detector 识别论证漏洞；
4. Questioner 生成 3-5 个候选追问；
5. Follow-up Judge 对候选追问进行筛选和排序；
6. 系统向用户展示最终追问；
7. 用户回答后系统重新评分，记录追问前后变化。

追问需要服务于测评目标，优先补充当前评分最需要的行为证据。挑战性和陷阱性追问需要受策略约束，不得直接暗示高分答案，不得引入与情境设定冲突的新事实，不得把用户引导到单一标准答案。

预期效果：AI 追问不再只是“请补充说明”，而是能够根据用户当前回答中缺失的证据、推理漏洞或新信息冲突，选择更有测评价值的问题。追问结果应帮助系统提升评分依据的充分性，同时保持测评过程自然、可控和可审计。

### 5.5 AI 评分与解释

本节一句话：AI 不只给分，还必须说明为什么给这个分，以及依据用户哪一句话给分。

系统需要基于六维审辩式思维模型进行评分：

1. 问题界定；
2. 证据评估；
3. 推理论证；
4. 多元视角；
5. 整合决策；
6. 动态调整。

每个维度采用 1-5 分量化评分，分值含义由 rubric/BARS 定义。评分结果需要同时保留量化分数和对应证据，避免只给出结论性评价。

每个维度评分需要包含：

1. 维度分数；
2. 证据句；
3. 评分理由；
4. 置信度；
5. 使用的 rubric 版本；
6. 使用的 prompt 版本。

1-5 分的基本解释如下，后续由心理测评相关成员进一步细化每个维度的行为锚点：

| 分值 | 基本含义 | 证据要求 |
| --- | --- | --- |
| 1 分 | 表现不足 | 回答缺少相关判断，或明显偏离情境任务 |
| 2 分 | 初步表现 | 能给出简单判断，但证据、推理或视角较弱 |
| 3 分 | 基本达标 | 能围绕问题给出较完整理由，并体现一定证据意识 |
| 4 分 | 良好表现 | 能综合多类信息，识别风险、权衡约束并提出合理方案 |
| 5 分 | 优秀表现 | 能系统界定问题，整合证据和多方视角，并在新信息下主动调整判断 |

评分结果需要可解释、可追溯、可导出。

预期效果：每个维度的评分都能回溯到用户原话、行为证据、评分标准和 AI 判断理由。心理测评相关成员可以复核评分合理性，开发成员可以稳定保存评分结果，用户报告也能避免只给结论而缺少依据。

### 5.6 反馈报告

本节一句话：把测评结果转化为用户能理解的反馈，而不是只展示一组分数。

系统需要面向测评用户生成个人反馈报告。报告内容包括：

1. 六维表现概览；
2. 主要优势；
3. 需要提升的方面；
4. 关键证据引用；
5. 发展建议；
6. 报告生成时间和评分版本信息。

报告面向用户展示，但报告快照不作为评分主数据源。评分主数据以维度评分、证据句和评分理由为准。

预期效果：用户能够看到自己的六维表现、主要优势、需要提升的方面和具体发展建议。报告中的每个关键结论应有对话证据支撑，同时避免把测评结果表述为诊断结论或唯一能力判定。

### 5.7 后台配置管理

本节一句话：把情境、评分、追问和报告模板做成可维护配置，避免后续每次调整都要改代码。

第一版系统需要支持后台可编辑配置，避免测评机制与代码强耦合。

后台至少支持维护：

1. 情境与情境阶段；
2. 六维 rubric；
3. 追问策略；
4. AI 提示词；
5. 专业知识上下文；
6. 报告模板；
7. 配置启用状态和版本号。

所有影响测评结果的配置都需要版本化。测评会话创建时需要记录实际使用的配置版本。

预期效果：心理测评相关成员可以持续优化维度定义、rubric、情境脚本和追问策略；开发成员可以通过配置版本追踪每次测评使用了哪一套规则。后续扩展多情境、多版本和专家修订时，系统不会因为规则写死在代码里而难以维护。

### 5.8 测评质量与验证需求

本节一句话：为后续证明“这个测评是否可靠、是否有效、是否公平”提前保留数据。

系统需要为后续信效度验证和评分机制优化保留必要数据。第一版不要求形成正式常模，但需要支持以下验证需求：

1. 内容效度审查：支持导出情境、阶段主问题、主测维度、评分标准和追问策略，供心理测评相关人员审阅。
2. 专家小样本评分：支持导出对话样本，支持录入或导入专家对六维维度的独立评分。
3. 人工评分一致性：支持计算或导出计算所需数据，用于比较不同专家评分的一致性。
4. AI 与人工评分一致性：支持比较 AI 评分和专家评分的相关、一致性和偏差。
5. 外部效标关联：支持将系统评分与 CCTST 等外部效标数据进行相关分析和高低组比较。
6. 追问有效性分析：支持比较追问前后新增证据、置信度变化和分数变化。
7. 异常样本分析：支持标记中途退出、无效回答、AI 输出异常、CCTST 缺失或 ID 不匹配等情况。
8. 公平性初步检查：支持按用户类型、教育阶段、专业背景等分组查看完成率、评分分布和异常率，识别潜在偏差。

预期效果：系统第一版虽然不直接形成正式常模，但能够为后续验证积累数据基础。团队可以通过专家评分、AI-人工一致性、外部效标关联和追问有效性分析，逐步判断测评工具是否具备继续优化和推广的价值。

### 5.9 AI Agent 质量控制需求

本节一句话：把 AI 能力拆成多个职责明确的子任务，并记录每次 AI 判断的输入、输出、版本和失败情况。

系统中的 AI 能力需要以 Agent 工作流组织，而不是单次无约束调用。第一版至少包括以下 Agent 或 AI 子任务：

1. Background Interviewer：负责背景采集和用户画像生成；
2. Host Agent：负责情境主持、阶段推进和施测节奏控制；
3. Scoring Agent：负责初评分、最终评分、证据句抽取和评分理由生成；
4. Gap Detector：负责识别评分缺口；
5. Argument Issue Detector：负责识别论证漏洞；
6. Questioner：负责生成候选追问；
7. Follow-up Judge：负责筛选候选追问；
8. Report Agent：负责生成用户报告。

每个 Agent 或 AI 子任务都需要满足以下要求：

1. 输入输出结构化：输入包含必要上下文，输出需要符合预设 JSON schema 或结构化格式；
2. 版本可追溯：记录使用的 prompt 版本、知识上下文版本、模型名称和关键参数；
3. 失败可恢复：模型调用失败、输出格式错误或内容明显异常时，系统保留用户原始输入并允许重试；
4. 诱导风险控制：追问不得直接暗示“高分答案”，不得误解用户原意，不得引入与情境无关的新事实；
5. 一致性控制：评分类 Agent 应使用较低随机性参数，必要时支持重复评分或多模型一致性检查；
6. 可审计：系统保存关键 AI 中间结果，包括评分缺口、论证漏洞、候选追问、Judge 理由和最终选择。

预期效果：AI 流程具备可控性和可追溯性。开发成员能够定位一次评分或追问是由哪个 Agent、哪个 prompt 版本、哪个模型配置生成的；心理测评相关成员能够复核 AI 判断是否符合评分标准和追问策略；系统出现异常时也能保留用户原始回答并支持重试。

| `KnowledgeResource` | 专业知识上下文 | 保存提供给 AI 的心理测评资料、专家示例和评分说明 | `resource_type`、`title`、`content`、`version_no`、`status` | `resource_type`：资料类型；`title`：资料标题；`content`：资料内容；`version_no`：资料版本 |
| `AgentRunLog` | Agent 运行日志 | 保存每次 AI 子任务调用的输入摘要、模型配置、输出状态和错误信息 | `session_id`、`agent_type`、`prompt_version_id`、`model_name`、`run_status`、`error_message` | `agent_type`：Agent 类型；`model_name`：模型名称；`run_status`：成功、失败或重试；`error_message`：错误说明 |
| `ExpertRating` | 专家评分 | 保存专家或人工评分者对样本对话的维度评分 | `session_id`、`rater_id`、`dimension`、`score`、`rating_reason`、`rated_at` | `rater_id`：评分者编号；`dimension`：评分维度；`score`：人工分数；`rating_reason`：人工评分理由 |
| `ValidationAnalysis` | 验证分析记录 | 保存阶段性信效度或评分一致性分析结果 | `analysis_type`、`sample_size`、`metric_name`、`metric_value`、`analysis_time` | `analysis_type`：分析类型，如外部效标相关、AI-人工一致性；`metric_name/value`：指标名称和值 |

数据字典中的中文说明主要用于需求对齐。后续逻辑结构设计阶段需要进一步明确字段类型、长度、是否必填、默认值、主键、外键、唯一约束和索引。

## 8. 性能需求

第一版面向小规模试测和演示场景，性能目标如下：

| 指标 | 目标 |
| --- | --- |
| 普通页面响应时间 | 1 秒内返回 |
| 对话提交接口响应时间 | 2 秒内完成入库，AI 结果可异步返回 |
| AI 追问生成时间 | 单轮建议控制在 5-15 秒 |
| 最终报告生成时间 | 建议控制在 30 秒内 |
| 单情境完整测评时长 | 建议控制在 30 分钟以内 |
| 单次测评阶段数量 | 建议控制在 5-7 个阶段 |
| 单次测评追问轮次 | 每个阶段建议控制在 0-2 轮追问 |
| 并发测评用户 | 初版支持 20-50 人同时测评 |
| 数据导出规模 | 支持导出 1000 条会话以内的数据 |

AI 调用受模型服务响应时间影响，系统需要提供加载状态、失败提示和重试机制。

## 9. 安全与隐私需求

系统涉及心理测评与个人背景信息，需要满足以下安全要求：

系统涉及个人背景信息、对话回答、测评结果和反馈数据，应遵循《个人信息保护法》关于知情同意、最小必要、目的限定、访问控制和安全保护的要求。

1. 测评用户采用匿名编号，不以真实姓名、手机号、学号作为主键；
2. 测评开始前需要展示知情同意说明，明确数据用途、保存范围和报告解释边界；
3. 管理后台需要登录认证；
4. 管理接口仅 `ADMIN` 可访问；
5. 用户原始回答、评分结果和外部效标数据需要限制访问；
6. 导出数据应默认使用匿名编号；
7. 不保存 CCTST 题目、截图或受版权保护的题本内容；
8. 关键配置变更需要记录操作人和操作时间；
9. AI 调用日志应避免包含无关敏感信息；
10. 用户报告需要展示解释边界，避免将测评结果表述为诊断结论或唯一能力判定；
11. 专家评分、外部效标和导出数据仅限后台授权用户访问；
12. 后续正式部署时应考虑 HTTPS、数据库备份和敏感字段加密；
13. 如后续提供数据删除、撤回授权或数据导出能力，需要记录处理状态和操作时间。

## 10. 非功能需求

| 类型 | 要求 |
| --- | --- |
| 可维护性 | 测评情境、rubric、追问策略、提示词和报告模板应支持后台配置 |
| 可追溯性 | 每次测评需要记录使用的配置版本、prompt 版本和评分版本 |
| 可解释性 | 评分必须包含证据句、评分理由和置信度 |
| 测评专业性 | 系统需要支持构念定义、测评蓝图、行为证据、评分标准和验证数据的统一管理 |
| 质量验证 | 系统需要支持专家评分、AI-人工一致性、外部效标关联和追问有效性分析所需的数据导出 |
| 公平性 | 系统需要支持按用户背景分组检查完成率、异常率和评分分布，减少构念无关因素影响 |
| AI 可审计性 | 系统需要记录关键 Agent 的输入摘要、输出结果、模型版本、prompt 版本和失败信息 |
| 可扩展性 | 数据模型应支持多情境、多版本、多轮追问和外部效标扩展 |
| 可导出性 | 系统需支持结构化导出，便于后续统计分析 |
| 可恢复性 | AI 调用失败时应保留用户原始回答，并允许重试 |
| 易用性 | 前台流程应减少表单感，突出交互式测评体验 |
| 模型可替换性 | 模型接入层应优先适配本土开源大模型，并避免与单一模型服务强绑定 |
| MCP 接入能力 | 系统应预留 MCP 协议接入能力，用于后续连接工具、知识资源或外部服务 |
| 时长可控性 | 系统需要通过阶段数量、追问轮次和超时控制保证单情境测评时长不超过 30 分钟 |

## 11. 需求阶段产出物

需求分析阶段产出物包括：

1. 需求规格说明书；
2. 数据字典初稿；
3. 核心业务流程说明；
4. 功能优先级列表；
5. 非功能需求清单；
6. 后续概要设计输入。

后续项目交付物需要在概要设计、详细设计和实现阶段继续补齐，至少包括：

1. 研发报告：包含能力模型论证、系统设计、评分算法、Agent 工作流和性能验证；
2. 可运行智能体原型：支持至少一个完整情境的多轮对话测评；
3. 代码与部署文档：说明前端、后端、数据库、模型服务和运行环境；
4. 完整测评情境脚本：包含情境背景、阶段主问题、动态信息更新、追问策略和评分证据点；
5. 评分规则说明：包含六维 1-5 分 rubric/BARS、证据句要求和评分解释规则；
6. 验证结果说明：包含专家评分、AI-人工一致性、外部效标关联和追问有效性分析的阶段性结果。
