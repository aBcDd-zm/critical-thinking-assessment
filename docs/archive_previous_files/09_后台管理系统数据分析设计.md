# Demo 2.0 后台管理系统数据分析设计

## 1. 设计定位

本后台不是运维监控面板，而是为心理学研究者设计的**测评质量分析工具**。它的核心任务是回答一个根本问题：这个测评工具到底能不能有效测量审辩式思维？

当前后台（`DashboardView.vue` + `/admin/dashboard/analytics`）主要回答"系统有没有正常运行"——会话数量、完成率、Agent 调用次数。Demo 2.0 需要升级为能回答"测评数据能不能用、评分靠不靠谱、追问有没有用"的分析工具。

## 3. 视角一：测评流程健康度

回答"测评有没有问题"——这一层保证数据本身的可用性。

### 3.1 测评漏斗

不只是一个完成率数字，而是按测评流程逐步展示每一步的留存情况。

```
开始测评 ──→ 完成第一轮回答 ──→ 完成全部阶段 ──→ 生成报告 ──→ 提交反馈
  100人         95人                82人              78人          65人
  (100%)        (95%)              (82%)            (78%)         (65%)
```

**API 设计**：`GET /admin/analytics/funnel`

```json
{
  "funnel": [
    {"stage": "session_created", "label": "开始测评", "count": 100, "rate": 1.0},
    {"stage": "first_turn", "label": "完成第一轮回答", "count": 95, "rate": 0.95},
    {"stage": "all_stages", "label": "完成全部阶段", "count": 82, "rate": 0.82},
    {"stage": "report_generated", "label": "生成报告", "count": 78, "rate": 0.78},
    {"stage": "feedback_submitted", "label": "提交反馈", "count": 65, "rate": 0.65}
  ],
  "drop_points": [
    {"from": "开始测评", "to": "完成第一轮回答", "loss": 5, "reason_hint": "用户在开场阶段退出，检查开场体验"},
    {"from": "完成全部阶段", "to": "生成报告", "loss": 4, "reason_hint": "4人完成对话但未触发生成报告，检查结束流程"}
  ]
}
```

**前端展示**：水平阶梯条形图，每步一个色块，宽度比例=留存率。流失点用红色虚线标注。每个色块可点击查看这步的会话列表。

### 3.2 阶段耗时分布

按六个阶段各自展示耗时分布，一眼看出哪个阶段让用户卡住了。

**API 设计**：`GET /admin/analytics/stages`

```json
{
  "stages": [
    {
      "stage_code": "s1",
      "title": "问题界定",
      "avg_duration_minutes": 3.2,
      "median_duration_minutes": 2.8,
      "p90_duration_minutes": 6.5,
      "avg_turns": 2.1,
      "avg_followups": 0.8,
      "completion_rate": 0.98,
      "anomalies": {
        "stuck_sessions": 2,
        "rushed_sessions": 0
      }
    }
  ]
}
```

**前端展示**：横向柱状图，六个阶段从上到下排列。每个柱体用颜色深浅区分"正常""偏长""异常长"。旁边挂一个微型热力条，展示该阶段下各 session 的耗时分布（点状散点图）。

**"stuck_sessions"判断标准**：某个阶段耗时超出该阶段 `estimated_minutes` 的 2 倍，且不是用户主动中断。

### 3.3 异常会话标记

自动标记而非手动标记。系统根据规则标注异常，研究者可以确认或解除。

| 异常类型 | 自动检测规则 | 严重程度 |
|---|---|---|
| 敷衍作答 | 所有回答 word_count < 10 | 高 |
| 中途退出 | status = aborted | 中 |
| 单轮超时 | 某轮回答耗时 > 5 分钟 | 低 |
| AI 频繁失败 | Agent 失败率 > 30% | 高 |
| 评分置信度过低 | 最终评分多个维度 confidence < 0.5 | 中 |
| 报告生成失败 | session 完成但无报告 | 高 |

**API 设计**：`GET /admin/analytics/anomalies?type=&page=1`

```json
{
  "total": 12,
  "items": [
    {
      "session_uuid": "abc-123",
      "participant_nickname": "小明",
      "anomaly_type": "low_effort",
      "severity": "high",
      "detail": "全部6轮回答字数均低于10字",
      "detected_at": "2026-07-01T10:00:00",
      "resolved": false
    }
  ]
}
```

**前端展示**：表格列表，可按类型和严重程度筛选。每行显示会话 uuid、用户昵称、异常类型、详情。点击会话 uuid 跳转到会话复盘页。

## 4. 视角二：用户表达充分性

回答"有没有采到足够的行为证据"——这是对话式测评区别于静态问卷的核心。

### 4.1 回答长度分布

不只是一个全局直方图，要能按阶段、按维度下钻。

**API 设计**：`GET /admin/analytics/expression/word-count?group_by=stage`

```json
{
  "global": {
    "bins": [
      {"range": "0-20字", "count": 45, "pct": 0.15},
      {"range": "20-50字", "count": 120, "pct": 0.40},
      {"range": "50-100字", "count": 90, "pct": 0.30},
      {"range": "100-200字", "count": 35, "pct": 0.12},
      {"range": "200+字", "count": 10, "pct": 0.03}
    ],
    "avg_word_count": 62.5,
    "median_word_count": 48
  },
  "by_stage": [
    {
      "stage_code": "s2",
      "title": "证据评估",
      "avg_word_count": 85.3,
      "bins": [
        {"range": "0-20字", "count": 8, "pct": 0.08},
        {"range": "20-50字", "count": 22, "pct": 0.22},
        {"range": "50-100字", "count": 35, "pct": 0.35},
        {"range": "100-200字", "count": 25, "pct": 0.25},
        {"range": "200+字", "count": 10, "pct": 0.10}
      ]
    }
  ]
}
```

**前端展示**：

- 全局：水平直方图，五段柱状，颜色从浅到深（浅=短回答，深=长回答）
- 按阶段下钻：六个迷你直方图并排，每个下面标注该阶段的平均字数。这样研究者一眼就能看到"多元视角阶段字数最少"，进而思考是追问不到位还是用户确实说不出。

### 4.2 追问有效性

核心指标：追问之后，用户有没有说出更多、有没有产生新证据。

**API 设计**：`GET /admin/analytics/expression/probe-effectiveness`

```json
{
  "by_type": [
    {
      "rule_type": "elaboration_probe",
      "label": "鼓励展开",
      "use_count": 45,
      "avg_word_delta": 38,
      "avg_new_evidence": 1.8,
      "confidence_gain": 0.12,
      "effectiveness_score": 0.78
    },
    {
      "rule_type": "clarify",
      "label": "澄清追问",
      "use_count": 30,
      "avg_word_delta": 8,
      "avg_new_evidence": 0.5,
      "confidence_gain": 0.03,
      "effectiveness_score": 0.35
    },
    {
      "rule_type": "challenge",
      "label": "挑战追问",
      "use_count": 22,
      "avg_word_delta": 42,
      "avg_new_evidence": 2.1,
      "confidence_gain": 0.18,
      "effectiveness_score": 0.85
    }
  ]
}
```

**关键计算说明**：

- `avg_word_delta`：追问后回答字数 - 追问前回答字数（同一阶段内相邻两轮用户回答对比）
- `avg_new_evidence`：追问后评分新增的 evidence 条数（基于 `ScoreSnapshot` 的过程性数据）
- `confidence_gain`：追问后评分置信度 - 追问前评分置信度
- `effectiveness_score`：综合评分（0-1），由以上三个指标归一化后加权计算

**前端展示**：散点图。X 轴 = 使用次数，Y 轴 = 效果分。每个追问类型是一个圆点，圆点大小 = 平均新增证据数。好的追问类型在右上角（用得多、效果好），差的在左下角。

### 4.3 六维证据覆盖雷达图

**API 设计**：`GET /admin/analytics/expression/evidence-coverage`

```json
{
  "dimensions": [
    {
      "dimension_key": "problem_definition",
      "name": "问题界定",
      "avg_evidence_count": 3.2,
      "avg_confidence": 0.78,
      "coverage_rate": 0.92,
      "low_coverage_session_count": 4
    }
  ]
}
```

**前端展示**：雷达图（六边形，六个维度各一个轴）。外层半透明色块 = 证据数量，内层线条 = 平均置信度。某个维度面积明显小，就用红色标记该轴。雷达图下方放一个小表格，列出每个维度的"证据不足会话数"。

## 5. 视角三：评分质量

回答"分数能不能信"——这一层直接关系到测评工具的信效度。

### 5.1 六维评分分布

**API 设计**：`GET /admin/analytics/scoring/distribution`

```json
{
  "dimensions": [
    {
      "dimension_key": "problem_definition",
      "name": "问题界定",
      "distribution": [
        {"score": 1, "count": 2, "pct": 0.04},
        {"score": 2, "count": 8, "pct": 0.16},
        {"score": 3, "count": 25, "pct": 0.50},
        {"score": 4, "count": 12, "pct": 0.24},
        {"score": 5, "count": 3, "pct": 0.06}
      ],
      "mean": 3.12,
      "std": 0.85,
      "skewness": -0.12,
      "ceiling_pct": 0.06,
      "floor_pct": 0.04
    }
  ]
}
```

**前端展示**：六个小型直方图并排（1x6 网格）。每个图只有 5 根柱子（1-5 分），柱子颜色渐变。评分均值用一条竖虚线标出。下面的关键指标展示在小卡片中：

| 指标 | 含义 | 优秀范围 |
|---|---|---|
| ceiling_pct | 5 分比例 | < 15%（太高说明没区分度） |
| floor_pct | 1 分比例 | < 15%（太高说明太苛刻） |
| std | 标准差 | > 0.7（太低说明全挤在中间） |

### 5.2 评分置信度分布

按维度展示 AI 对自己评分的确定性。

**API 设计**：`GET /admin/analytics/scoring/confidence`

```json
{
  "dimensions": [
    {
      "dimension_key": "problem_definition",
      "name": "问题界定",
      "avg_confidence": 0.82,
      "low_confidence_pct": 0.12,
      "confidence_bins": [
        {"range": "0-0.5", "count": 6, "pct": 0.12},
        {"range": "0.5-0.7", "count": 8, "pct": 0.16},
        {"range": "0.7-0.9", "count": 20, "pct": 0.40},
        {"range": "0.9-1.0", "count": 16, "pct": 0.32}
      ]
    }
  ]
}
```

**前端展示**：和评分分布一样，六个迷你直方图并排。但这里 X 轴是置信度区间。低置信度（<0.5）占比高的维度用红色标记——说明 AI 对这个维度不太有把握，可能是 rubric 不够明确或该维度的证据难以从对话中识别。

### 5.3 证据-分数一致性

检查同一个分数背后的证据质量是否一致。

**API 设计**：`GET /admin/analytics/scoring/evidence-consistency`

```json
{
  "dimension": "problem_definition",
  "score_levels": [
    {
      "score": 3,
      "sample_count": 25,
      "avg_evidence_count": 2.1,
      "std_evidence_count": 0.9,
      "evidence_type_distribution": {
        "support": 75,
        "counter": 10,
        "invalid": 15
      }
    }
  ]
}
```

**前端展示**：散点图。X 轴 = 分数，Y 轴 = 证据数量。每个 session 一个点。如果同一个分数（比如 3 分）下，有的 session 只有 1 条 evidence，有的有 5 条，那说明评分一致性有问题——圆点在同一条垂线上分散太广。

## 6. 视角四：个体会话深度复盘

回答"这个人为什么得了这个分"——这是 Demo 2.0 最重要的展示点。单页让研究者在 3 分钟内理解一个人的测评全过程。

### 6.1 会话搜索与列表

在"会话复盘"Tab 中，默认展示一个搜索结果列表。

**API 设计**：复用并扩展现有的 session 列表接口。

```json
{
  "sessions": [
    {
      "session_uuid": "abc-123",
      "participant_nickname": "小明",
      "scenario_title": "产品上线前48小时",
      "status": "completed",
      "turn_count": 14,
      "total_duration_minutes": 22,
      "overall_score": null,
      "anomaly_count": 0,
      "has_report": true,
      "completed_at": "2026-07-01T10:00:00"
    }
  ]
}
```

**筛选条件**：状态、异常类型、最少轮次、日期范围、六维分数范围。

### 6.2 单会话复盘页 —— 核心页面

路由：`/admin/sessions/:sessionUuid/review`

这是整个后台分析中最重要的一个页面。它不是一个数据堆砌页，而是一个让研究者能"用眼睛读"一个人的测评过程的叙事型页面。

**页面分五个区域**：

#### 区域 A：概览条（页面顶部，始终可见的粘性条）

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 小明 · 产品上线前48小时 · 22分钟 · 14轮对话 · 2026-07-01 10:00          │
│ ●●◐○○ 问题界定4 证据评估3 推理论证4 多元视角2 整合决策3 动态调整3       │
│ [标记异常] [导出此会话]                                         [返回列表] │
└─────────────────────────────────────────────────────────────────────────┘
```

概览条中的每个维度分数是一个圆点，颜色 = 分数对应的色阶（红=1，黄=3，绿=5）。点击某个维度可以跳转到下面的评分详情区。

#### 区域 B：对话时间线（页面中央，核心内容）

按时间顺序展示全部对话。但每条消息有不同视觉权重：

```
  ┌─ 阶段1 · 问题界定 ──────────────────────────────────────────┐
  │                                                               │
  │  AI · 开场问                                                 │
  │  ┌──────────────────────────────────────────────────────┐    │
  │  │ 🤖 面试官  追问类型：开场提问（host）                   │    │
  │  │ 你先按自己的理解说说，这件事最让你卡住的地方是什么      │    │
  │  └──────────────────────────────────────────────────────┘    │
  │                                                               │
  │  用户 · 第3轮（耗时 1:23 · 78字 · 文字输入）                  │
  │  ┌──────────────────────────────────────────────────────┐    │
  │  │ 👤 小明                                                │    │
  │  │ 我觉得最核心的问题是上线时间的选择。现在有两种声音，   │    │
  │  │ 开发团队希望延期因为他们发现了几个高优先级的缺陷，     │    │
  │  │ ▓▓▓▓▓▓ 但市场那边说竞品下周就要发新版了 ▓▓▓▓▓▓      │    │
  │  │       ↑ 被引用为「问题界定」4分证据                   │    │
  │  └──────────────────────────────────────────────────────┘    │
  │                                                               │
  │  AI · 追问                                                    │
  │  ┌──────────────────────────────────────────────────────┐    │
  │  │ 🤖 面试官  追问类型：elaboration_probe（鼓励展开）     │    │
  │  │   追问目标：引导用户说明判断优先级的具体标准            │    │
  │  │ 你说的两种声音很有价值，你是怎么衡量"高优先级缺陷"和   │    │
  │  │ "竞品发布窗口"这两个因素的？                           │    │
  │  └──────────────────────────────────────────────────────┘    │
  │                                                               │
  │  用户 · 第4轮（耗时 2:05 · 145字 · 语音输入）  ← 语音标记   │
  │  ┌──────────────────────────────────────────────────────┐    │
  │  │ 👤 小明                                                │    │
  │  │ 我会先判断缺陷是否影响核心用户路径...                   │    │
  │  │ ...如果一个缺陷会导致用户无法完成支付流程，那它一定    │    │
  │  │ 是阻塞性的。但如果只是UI上的小问题...                   │    │
  │  │ ▓▓▓▓▓▓ 我会判断缺陷是否影响核心用户路径 ▓▓▓▓▓▓        │    │
  │  │ ▓▓▓▓▓▓ 缺陷导致用户无法完成支付流程是阻塞性的 ▓▓▓▓▓▓  │    │
  │  │       ↑ 两条都被引用为证据                             │    │
  │  └──────────────────────────────────────────────────────┘    │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘
```

**视觉规则**：

- AI 消息：浅灰底 + 左侧竖线（追问类型不同颜色：绿色=展开，蓝色=澄清，橙色=挑战，红色=陷阱）
- 用户消息：白色底 + 右侧细边框
- **被引用为证据的句子**：黄色高亮背景（`background: #fff3dc`）+ 下划线 + 旁边标注维度名称和分数
- **低信息回答**：整条消息红色细边框，消息顶部有一个"⚠️ 本轮回答信息量不足"的标签
- **动态信息释放**：消息之间插入一条蓝色横线，标注"⚡ 此时释放了新信息：核心功能在灰度环境出现高频报错"
- **Fallback 追问**：AI 消息顶部有一个小标签"⚠️ 使用了兜底追问"
- **语音输入的消息**：用户头像旁边有一个小喇叭图标

这是整个页面最关键的设计决策——研究者不需要在对话和证据表之间来回对照，一切都在同一条时间线里。

## 9. 图表库选择

当前前端没有任何图表库依赖。Demo 2.0 引入了多种图表需求，建议加一个轻量图表库。

推荐 **Chart.js v4**（通过 CDN 或 npm 安装）。理由：

- 现有后端 artifact 设计文档已经推荐过 Chart.js（CDN）
- 支持直方图、散点图、雷达图、漏斗图——覆盖全部需求
- 体量小（gzip 后约 60KB）
- 不需要额外 CSS，Canvas 渲染

```bash
npm install chart.js
```

或者直接用 `chart.js` CDN 在 `index.html` 中引入。对于比赛原型来说 CDN 更简单。
