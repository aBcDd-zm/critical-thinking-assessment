# 全栈B与全栈C后续开发任务分配

本文档用于在当前项目基线已经跑通后，重新拆分全栈 B 和全栈 C 的后续开发任务。当前阶段的核心目标不是重新搭项目框架，而是在已有 FastAPI + MySQL + Vue 基线之上，把“对话测评流程”和“评分报告生成”两条 Agent 主线做稳。

### 1.2 最近一次完整对话测试结论

最新完整测试结果显示：系统已经可以完成一次从进入测评到结束测评的完整交互流程。测试会话共 41 条 DialogueTurn、25 条 AgentTrace，6 个阶段均被推进，AgentTrace 未出现失败记录。

这说明当前项目已经具备可演示的主流程，但也暴露出几类需要尽快修复的问题：

| 问题 | 现象 | 影响 | 归属 |
| --- | --- | --- | --- |
| 动态信息重复释放 | 同一 `dynamic_info_id` 在同一阶段被多次释放，例如 `sample_bias_warning`、`support_capacity_warning`、`error_rate_increase` | 用户体验重复，测评流程显得不够专业；后续评分可能重复引用同一信息 | 全栈 B |
| 动态信息显示与 Trace 不完全一致 | 某些 trace 记录选中了动态信息，但 AI 实际回复中没有清晰呈现该动态信息原文 | 可追溯性受影响，后台记录和用户实际看到的内容可能不一致 | 全栈 B |
| 低信息回答兜底不够阶段化 | 用户在后续阶段回答“无 / 不知道 / 没有方案”时，有时仍触发第一阶段风格的“核心问题是什么”追问 | 追问与当前阶段目标不完全匹配 | 全栈 B |
| 阶段推进较机械 | 某阶段有效回答不足时仍会进入下一阶段 | 测评可完成，但应标记“证据不足”或“低置信度”，否则评分解释会失真 | 全栈 B + 全栈 C |
| 评分报告未生成 | 测评结束后 `assessment_report` 仍为空 | 用户无法看到六维评分、证据解释、优势和改进建议 | 全栈 C |
| 低质量回答未形成评分证据 | 多次“不知道 / 无 / 没方案”目前只体现在对话文本中，还没有转成低分、低置信度或无效证据 | 测评结果缺少专业解释 | 全栈 C |

## 2. 本阶段目标

本阶段只聚焦两条主线：

1. 全栈 B：优化对话流程，让 AI 追问更稳定、更可追溯、更贴合阶段目标。
2. 全栈 C：实现评分与最终报告生成，让一次 completed session 能生成结构化测评报告。

本阶段完成后，系统应达到：

1. 用户完成一次测评后，数据库里能看到完整 DialogueTurn、AgentTrace、ScoreSnapshot、ScoreResult、ScoreEvidence、AssessmentReport；
2. 同一动态信息在同一 session 中不会被重复释放；
3. 用户看到的动态信息文本和数据库记录能够对应；
4. 低信息回答能被按阶段兜底处理，并能在评分中体现低证据质量；
5. 前端报告页可读取并展示最终报告 JSON；
6. B/C 各自模块可用脚本验收，不需要只靠人工聊天体验判断。

## 5. 全栈 B 任务卡片：对话流程优化

### DEV-B-001 动态信息释放去重

| 项目 | 内容 |
| --- | --- |
| 目标 | 同一个 session 内，同一条动态信息只释放一次 |
| Owner | 全栈 B |
| 优先级 | P0 |
| 依赖 | 当前 `DialogueTurn.dynamic_info_id` 已能保存 |
| 主要文件 | `dialogue_policy.py`、`mock_dialogue.py`、`followup_agent.py` |
| 不允许改动 | 数据库模型、migration |

实现要求：

1. 判断动态信息是否已释放时，必须优先使用 `DialogueTurn.dynamic_info_id` 或 `selected_dynamic_info_code`，不能只靠文本包含判断；
2. 已释放的 `StageDynamicInfo` 不得再次作为新动态信息释放；
3. 如果动态信息已经释放，但用户回答仍然低质量，可以继续追问，但不能重复包装为“现在补充一条新信息”；
4. Trace 中应保留本次是否释放动态信息的判断原因。

验收标准：

1. 一次完整 session 中，同一个 `dynamic_info_id` 在 `dialogue_turn` 中最多出现一次；
2. 用低信息回答连续触发同一阶段追问时，不会重复释放同一动态信息；
3. 新增或更新脚本能自动检查重复释放问题。

建议验收命令：

```powershell
cd backend
.\.venv\Scripts\python.exe scripts\check_agent_contract.py
.\.venv\Scripts\python.exe scripts\check_mock_assessment_flow.py --skip-db
```

建议新增：

```text
backend/scripts/check_dialogue_dynamic_info_once.py
```

### DEV-B-002 动态信息强制可见

| 项目 | 内容 |
| --- | --- |
| 目标 | 选中动态信息后，用户实际看到的文本必须包含该动态信息的核心内容 |
| Owner | 全栈 B |
| 优先级 | P0 |
| 依赖 | DEV-B-001 |
| 主要文件 | `dialogue_text_streamer.py`、`mock_dialogue.py`、`followup_agent.py` |

实现要求：

1. 当 `selected_dynamic_info_code` 不为空时，AI 输出中必须明确呈现该动态信息；
2. 推荐格式为“固定动态信息文本 + AI 生成追问”，不要完全交给模型自由改写；
3. 如果走 token 流式，动态信息文本可以先作为固定 delta 发给前端，再流式生成后半段追问；
4. `released_dynamic_info_text` 必须与用户可见文本对应；
5. 不允许 Trace 记录释放了某条动态信息，但用户文本里完全看不到该信息。

验收标准：

1. 查询 `dialogue_turn.dynamic_info_id is not null` 的记录时，`dialogue_turn.content` 能找到对应 `stage_dynamic_info.content` 的核心内容；
2. `AgentTrace.output_json.released_dynamic_info_text` 不为空，且与 `DialogueTurn.content` 能对应；
3. 用户体验上，动态信息不是“隐形地影响模型”，而是明确展示给用户。

### DEV-B-003 低信息回答阶段化兜底

| 项目 | 内容 |
| --- | --- |
| 目标 | 用户回答“无 / 不知道 / 没方案”等低信息内容时，按当前阶段生成合适兜底问题 |
| Owner | 全栈 B |
| 优先级 | P0 |
| 依赖 | 当前 `_build_invalid_answer_followup` 已有基础兜底 |
| 主要文件 | `dialogue_policy.py`、`dialogue_text_streamer.py`、`mock_dialogue.py` |

实现要求：

按阶段设计兜底问题，不允许所有阶段都问“核心问题是什么”。

| 阶段 | 低信息回答兜底方向 |
| --- | --- |
| s1 问题界定 | 请用户用一句话说明当前核心决策问题 |
| s2 证据核实 | 请用户说出一个最应该核实的证据，以及为什么 |
| s3 多方视角 | 请用户说出一个必须考虑的角色或团队诉求 |
| s4 推理论证 | 请用户先给出一个初步方案倾向，并说明一个理由 |
| s5 动态调整 | 请用户说明新信息带来的一个直接风险或调整点 |
| s6 最终方案 | 请用户先给出一个上线策略倾向，例如按时、延期、灰度或其他 |

验收标准：

1. 在 6 个阶段分别输入“我不知道”，AI 兜底问题与当前阶段目标匹配；
2. 兜底输出不能暴露评分标准；
3. 兜底输出不能捏造用户说过的内容；
4. 兜底输出仍然保存为 `DialogueTurn` 和 `AgentTrace`。

### DEV-B-004 阶段推进质量标记

| 项目 | 内容 |
| --- | --- |
| 目标 | 阶段有效证据不足时可以推进，但必须留下质量标记，供评分 Agent 使用 |

| 优先级 | P1 |
| 依赖 | DEV-B-003 |
| 主要文件 | `dialogue_policy.py`、`followup_agent.py`、`mock_dialogue.py` |

3. `reason` 中说明阶段推进原因，例如“追问次数达到上限，但有效证据不足”；
4. 该标记后续应能被全栈 C 的 ScoringAgent 读取，用于低分或低置信度判断。

验收标准：

1. 用户连续低信息回答后阶段推进，AgentTrace 中能看到 warning；
2. 正常高质量回答推进时，不应误标低信息；
3. 不影响完整测评流程结束。

## 6. 全栈 C 任务卡片：评分与报告生成

### DEV-C-001 ScoringAgent 基础实现

| 项目 | 内容 |
| --- | --- |
| 目标 | 基于完整对话、rubric 和阶段目标生成六维评分 |
| Owner | 全栈 C |
| 优先级 | P0 |
| 依赖 | `ScoringOutput`、`DimensionScore`、`EvidenceItem` schema 已存在 |
| 主要文件 | `scoring_agent.py`、`mock_scoring_report.py`、`scoring_prompts.py` |

实现要求：

1. 输出必须符合 `backend/app/agents/schemas.py` 中的 `ScoringOutput`；
2. 六个维度均需给出 1-5 分，至少包括：问题界定、证据评估、推理论证、多元视角、整合决策、动态调整；
3. 每个维度必须有 `reason`；
4. 关键维度必须有来自用户原话的 evidence；
5. 对“无 / 不知道 / 没方案”等回答，应识别为低证据质量，不能强行给高分；
6. `detected_score_gaps` 和 `detected_argument_issues` 需要可用于后续追问或报告解释。

验收标准：

1. mock 模式无 API Key 可运行；
2. 至少 3 组测试样例：低质量回答、中等回答、较高质量回答；
3. 分数、置信度、证据句均符合 schema；
4. 证据句不能编造，必须来自 `dialogue_history`。

### DEV-C-002 证据抽取与无效证据识别

| 项目 | 内容 |
| --- | --- |
| 目标 | 将用户原话映射到评分证据，并识别低信息或无效证据 |
| Owner | 全栈 C |
| 优先级 | P0 |
| 依赖 | DEV-C-001 |
| 主要文件 | `scoring_agent.py`、`rag_context.py`、`scoring_prompts.py` |

实现要求：

1. Evidence 必须保留 `dialogue_turn_id`；
2. `evidence_type` 至少支持 `supporting_evidence`、`weak_evidence`、`invalid_evidence`；
3. 对低信息回答要能形成无效证据说明，例如“用户未提供具体判断”；
4. 如果某维度没有足够证据，不允许编造证据，应降低置信度并写入 `detected_score_gaps`；
5. 能利用 rubric 中的可观察行为、无效证据说明和评分锚点。

验收标准：

1. 对完整测试 session 中的多次“不知道”，能识别为低质量证据；
2. 对“运营团队服务质量下降，获得用户差评”这类具体回答，能抽取为多方视角或风险判断相关证据；
3. 输出中每条 evidence 都能追溯到某条 DialogueTurn。

### DEV-C-003 ReportAgent 基础实现

| 项目 | 内容 |
| --- | --- |
| 目标 | 基于评分结果生成面向用户的结构化报告 |
| Owner | 全栈 C |
| 优先级 | P0 |
| 依赖 | DEV-C-001、DEV-C-002 |
| 主要文件 | `report_agent.py`、`report_prompts.py`、`mock_scoring_report.py` |

实现要求：

1. 输出必须符合 `ReportOutput`；
2. 报告必须包含总评、六维分项报告、优势、改进建议、发展计划和免责声明；
3. 每个维度报告至少包含：维度名、分数、等级、优势或不足、证据引用、建议；
4. 报告语言面向用户，不能写成内部调试日志；
5. 不得使用诊断性、医学性或高风险选拔结论；
6. 对低质量回答较多的用户，应明确说明“本次证据有限，结果置信度较低”。

验收标准：

1. 一个 completed session 可以生成合法 `ReportOutput`；
2. 报告中引用的证据句来自用户对话；
3. 报告 JSON 可直接给前端展示；
4. 报告包含清晰免责声明。

## 7. B/C 接口契约

### 7.1 B 输出给后端的核心契约

B 的对话输出以 `FollowupOutput` / `HostOutput` 为准。关键字段：

| 字段 | 要求 |
| --- | --- |
| `question` / `message` | 用户实际可见文本 |
| `content_type` | `followup_question`、`dynamic_info_question`、`advance_prompt` 等 |
| `selected_rule_code` | 使用了追问规则时必须填写 |
| `selected_dynamic_info_code` | 释放动态信息时必须填写 |
| `released_dynamic_info_text` | 释放动态信息时必须填写，且应能在用户可见文本中找到 |
| `next_action` | `ask_followup`、`advance_stage`、`finish_ready` 等 |
| `warnings` | 低信息回答、证据不足、fallback 等情况必须记录 |

### 7.2 C 输出给后端的核心契约

C 的评分报告输出以 `ScoringOutput` / `ReportOutput` 为准。关键字段：

| 字段 | 要求 |
| --- | --- |
| `scores[].dimension_key` | 必须匹配 rubric 维度 key |
| `scores[].score` | 1-5 整数 |
| `scores[].confidence` | 0-1 |
| `scores[].evidence` | 必须来自对话原文 |
| `detected_score_gaps` | 说明证据不足或能力缺口 |
| `dimension_reports` | 六维报告展示数据 |
| `disclaimer` | 必须存在 |
