# 访谈式追问机制优化方案

## 1. 文档目标

本文用于说明 Demo 2.0 阶段用户端访谈流程与追问机制的优化方案。

本次优化的核心不是单纯调整提示词话术，而是重新梳理“数字面试官如何提问、如何追问、如何在后台保留可评分证据”的整体机制，使系统更符合老师提出的方向：让用户像面对一位数字面试官一样自然表达，多讲自己的判断、理由、证据、权衡和行动计划。

本文重点回答四个问题：

1. 当前提问与追问为什么效果不够好；
2. 新的访谈式追问机制应该遵循什么原则；
3. 这套机制如何落到现有业务流程与数据模型中；
4. 后续应如何分阶段实现与验收。

## 2. 当前问题分析

### 2.1 阶段主问题存在复合提问

当前第一阶段主问题类似：

> 你认为当前最核心的决策问题是什么？你会怎样界定这个问题？

这实际上包含两个认知任务：

1. 识别当前最核心的决策问题；
2. 解释自己如何界定这个问题。

对受测者来说，这会增加回答负担。用户可能只回答前半部分，也可能只回答后半部分，系统后续很难判断用户到底是哪一部分没有展开。

因此，阶段主问题应遵循“单问题原则”：每次只让用户回答一个清晰问题。

### 2.2 当前追问仍然偏收束

当前追问示例：

> 如果现在必须在上线时间和产品稳定性之间做一个取舍，你觉得这两者之间是什么关系？

这句话虽然加入了“没有标准答案”“我更想听直觉”等人本主义表达，但本质上仍然把用户限制进了“上线时间 vs 产品稳定性”的二元框架。

用户原本可能想谈：

- 资源分配；
- 用户信任；
- 灰度发布；
- 风险验证；
- 团队沟通；
- 运营承载；
- 品牌影响。

但追问提前把问题框定为两个因素之间的关系，会压缩用户自由发挥空间。

### 2.3 问题本质

当前系统的问题不是“不够温柔”，而是仍然在用预设测评框架牵引用户回答。

老师希望的方向是：

> 前台像访谈，后台像测评。

也就是说，用户看到的是开放、自然、低压的访谈问题；系统后台仍然使用六维能力模型、rubric、证据句和 AgentTrace 进行结构化分析。

## 3. 优化目标

### 3.1 产品体验目标

用户应感受到自己是在和数字面试官自然交流，而不是在填写问卷或参加考试。

优化后的体验应具备以下特点：

- 问题短；
- 每次只问一个问题；
- 不要求用户按固定格式回答；
- 不提前限定用户只能从某几个角度回答；
- 优先顺着用户已经表达的内容继续追问；
- 鼓励用户讲更多自己的判断过程。

### 3.2 测评机制目标

系统后台仍然需要保证测评的专业性和可解释性。

因此，开放式访谈并不等于自由聊天。每一轮追问仍然需要绑定：

- 当前情境；
- 当前阶段；
- 目标能力维度；
- 触发原因；
- 证据缺口；
- 追问策略；
- Agent 输出记录。

### 3.3 数据模型目标

第一版不建议新增物理表，优先复用现有模型：

- `ScenarioStage` 控制阶段目标与第一问；
- `StageInterventionRule` 控制追问策略方向；
- `question_generation_constraints_json` 控制追问边界；
- `DialogueTurn` 保存用户实际看到或说出的文本；
- `AgentTrace.output_json` 保存追问背后的结构化决策过程。

## 4. 核心设计原则

### 4.1 单问题原则

每次只问一个问题。

错误示例：

> 你认为当前最核心的决策问题是什么？你会怎样界定这个问题？

优化示例：

> 如果你是项目负责人，看到这个情况后，你最想先弄清楚的问题是什么？

用户回答后，再根据情况追问：

> 你愿意多说说，为什么这个问题会成为你最先关注的点吗？

### 4.2 低指向前台，高结构后台

用户可见问题应尽量开放，不直接暴露测评框架。

后台可以知道本阶段主要观察“问题界定”，但前台不应直接要求用户按照“问题界定、证据评估、推理论证”等维度作答。

设计原则：

> 前台问题低指向，后台评分高结构。

### 4.3 优先使用用户原话

追问应尽量基于用户已经说过的内容，而不是主动引入用户没有提到的新框架。

例如用户说：

> 我觉得市场窗口很重要。

优化追问：

> 你刚才提到市场窗口很重要，可以多说说为什么它在你这里排得这么靠前吗？

不建议追问：

> 那你觉得市场窗口和产品稳定性之间应该如何取舍？

因为后者主动引入了“产品稳定性”这个框架，如果用户尚未提到它，就会限制自由表达。

### 4.4 先展开，再证据化

追问不应一开始就要求用户给出完整证据链，而应先让用户展开想法。

推荐顺序：

1. 自由展开：你可以多说说为什么会这样想吗？
2. 具体化：这个判断主要基于哪些信息？
3. 权衡化：如果出现不同意见，你会怎么看？
4. 行动化：接下来你会先做什么？

这样既能增加表达量，也能逐步形成可评分证据。

### 4.5 不提前塞入标准答案路径

追问不能暗示高分答案。

不建议：

> 你会不会考虑灰度发布、验证数据和回滚方案？

这会提示用户应该说哪些内容。

推荐：

> 如果你要继续推进这个判断，你接下来最想确认哪一件事？

这样用户仍有自由发挥空间，系统也能观察其证据意识和行动计划。

## 5. 优化后的业务流程

### 5.1 阶段开场

系统先展示情境背景，然后提出一个开放的单问题。

以第一阶段为例：

当前版本：

> 如果你是项目负责人，你认为当前最核心的决策问题是什么？你会怎样界定这个问题？

建议版本：

> 如果你是项目负责人，看到这个情况后，你最想先弄清楚的问题是什么？

### 5.2 用户自由回答

用户可以从任何角度回答，不要求按照系统预设结构。

系统保存用户原始回答到 `DialogueTurn`。

### 5.3 FollowupAgent 分析回答

FollowupAgent 不应立即纠偏，而应先判断：

- 用户是否给出了明确关注点；
- 用户是否解释了为什么关注该点；
- 用户是否提到证据、风险、影响、角色或行动；
- 当前是否存在可评分证据缺口；
- 是否需要继续让用户展开。

### 5.4 生成开放式追问

追问优先采用以下类型：

| 追问类型 | 目的 | 示例 |
| --- | --- | --- |
| 自由展开 | 鼓励用户多说 | 你可以多说说为什么会这样看吗？ |
| 原话延展 | 顺着用户关键词追问 | 你刚才提到“市场窗口”，它为什么对你很关键？ |
| 具体化 | 让抽象判断变具体 | 你觉得这个风险会具体影响到谁或哪一环？ |
| 判断依据 | 收集证据 | 这个判断主要来自哪些信息？ |
| 权衡过程 | 观察推理 | 如果有人不同意你的判断，你会怎么回应？ |
| 行动计划 | 观察整合决策 | 如果由你推进，第一步会做什么？ |

### 5.5 后台记录追问质量

每次追问除了保存用户可见文本，还应在 `AgentTrace.output_json` 中记录：

- 本轮追问意图；
- 是否单问题；
- 是否使用用户原话；
- 是否引入用户未提及框架；
- 是否暗示标准答案；
- 本轮追问对应的能力维度；
- 当前证据缺口。

## 6. 数据模型落地方案

### 6.1 `scenario_stage.main_question`

`main_question` 表示阶段开场时用户看到的第一问。

建议约束：

- 只包含一个问题；
- 不要求用户同时完成多个认知任务；
- 不直接暴露评分维度；
- 不提前限制回答角度；
- 尽量以开放问题引导用户表达。

示例：

```yaml
main_question: 如果你是项目负责人，看到这个情况后，你最想先弄清楚的问题是什么？
```

不建议：

```yaml
main_question: 如果你是项目负责人，你认为当前最核心的决策问题是什么？你会怎样界定这个问题？
```

### 6.2 `stage_intervention_rule.strategy_direction`

`strategy_direction` 保存内部追问策略方向，不等于用户可见话术。

建议写法：

```yaml
strategy_direction: 引导用户围绕自己提出的关注点继续展开，观察其是否能自然呈现问题界定依据。
```

不建议写法：

```yaml
strategy_direction: 引导用户区分上线时间压力和产品质量风险。
```

后者过于收束，容易让模型主动引入二元框架。

### 6.3 `stage_intervention_rule.sample_question`

`sample_question` 是给 AI 的参考问法，不要求原样使用。

建议从“收束型问题”改为“开放采样型问题”。

建议示例：

```yaml
sample_question: 你刚才提到的这个点，为什么会成为你最先关注的问题？
```

不建议：

```yaml
sample_question: 上线时间压力和产品质量风险之间是什么关系？
```

### 6.4 `stage_intervention_rule.question_generation_constraints_json`

这是本方案最关键的配置字段。

建议加入以下结构：

```json
{
  "interview_style": "humanistic_non_directive",
  "max_visible_questions": 1,
  "user_freedom_level": "high",
  "must_use_user_words": true,
  "forbidden_framing": [
    "不得引入用户没有提到的二元取舍",
    "不得要求用户用一句话概括",
    "不得提前给出上线/延期/灰度等选项",
    "不得把追问写成标准答案提示"
  ],
  "allowed_probe_modes": [
    "free_elaboration",
    "user_word_extension",
    "reasoning_path",
    "concrete_consequence",
    "personal_priority",
    "evidence_source",
    "action_next_step"
  ]
}
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `interview_style` | 追问风格，建议使用非指令性人本主义访谈 |
| `max_visible_questions` | 单次用户可见问题数量，建议为 1 |
| `user_freedom_level` | 用户自由发挥空间，第一版建议高 |
| `must_use_user_words` | 是否优先使用用户原话继续追问 |
| `forbidden_framing` | 禁止引入的限制性框架 |
| `allowed_probe_modes` | 允许使用的追问模式 |

### 6.5 `dialogue_turn`

`dialogue_turn` 只保存用户实际看到或说出的文本。

不在该表中保存：

- 追问意图；
- 证据缺口；
- 追问质量标记；
- 是否引入限制性框架；
- 人本主义访谈结构。

这些信息属于 Agent 过程数据，应保存到 `agent_trace.output_json`。

### 6.6 `agent_trace.output_json`

建议扩展追问 Agent 的输出结构：

```json
{
  "question": "你刚才提到市场窗口很重要，可以多说说为什么它在你这里排得这么靠前吗？",
  "followup_intent": "user_word_extension",
  "target_dimensions": ["problem_definition"],
  "trigger_reason": "用户给出了初步关注点，但尚未说明该关注点的重要性",
  "reflection_summary": "用户认为市场窗口是当前重要因素",
  "evidence_gap": "缺少用户为什么优先关注市场窗口的解释",
  "user_freedom_level": "high",
  "visible_question_count": 1,
  "introduced_assumptions": [],
  "quality_flags": {
    "single_question": true,
    "uses_user_words": true,
    "no_binary_framing": true,
    "no_standard_answer_hint": true,
    "no_forced_format": true
  },
  "humanistic_steps": {
    "listening_acknowledgement": "接住用户提到市场窗口的关注点",
    "reflective_clarification": "用户当前表达了关注点，但原因尚未展开",
    "safety_prompt": "不要求标准答案，重点是理解判断过程",
    "evidence_probe": "为什么市场窗口在你这里排得这么靠前？"
  }
}
```

### 6.7 是否需要新增表

第一版不建议马上新增表。

原因：

- 当前已有模型可以承载该机制；
- 新增表会增加迁移、后台管理和任务分工成本；
- 当前最急的是把访谈效果跑顺。

但如果后续要进一步规范化，可以考虑新增 `stage_question_item` 表，将一个阶段拆成多个可配置问题节点。

预留设计：

| 字段 | 说明 |
| --- | --- |
| `id` | 问题节点 ID |
| `stage_id` | 所属阶段 |
| `question_code` | 问题编码 |
| `question_order` | 问题顺序 |
| `question_text` | 用户可见问题 |
| `question_role` | opening、probe、transition |
| `target_dimensions` | 目标维度 |
| `openness_level` | 开放程度 |
| `is_required` | 是否必问 |
| `trigger_condition` | 触发条件 |
| `status` | 状态 |

该表属于 V2 规范化方向，第一版暂不实施。

## 7. Agent 生成策略调整

### 7.1 HostAgent

HostAgent 负责阶段开场。

调整要求：

- 只提出一个阶段主问题；
- 不把多个问题合并到一句话中；
- 不要求用户一次性完成完整分析；
- 保持数字面试官的自然口吻。

### 7.2 FollowupAgent

FollowupAgent 负责追问。

调整要求：

- 每次只输出一个用户可见问题；
- 优先使用用户原话；
- 不引入用户未提及的二元框架；
- 不提前给出选项；
- 不要求用户按固定格式回答；
- 优先引导用户展开，而不是立刻纠偏；
- 内部仍需记录目标维度和证据缺口。

### 7.3 追问质量检查

建议增加一个轻量的追问质量检查逻辑。

检查项：

| 检查项 | 判断方式 |
| --- | --- |
| 是否单问题 | 用户可见文本中问号数量不超过 1，或语义上只有一个核心问题 |
| 是否使用用户原话 | 追问中是否包含用户上一轮回答的关键词 |
| 是否引入未提及框架 | 是否出现用户未提及的强制二元取舍 |
| 是否暗示标准答案 | 是否出现“你是否应该考虑 A、B、C”式提示 |
| 是否强制格式 | 是否要求用户“用一句话”“按三点说明”等 |

如果质量检查不通过，可以降级为开放兜底问题：

```text
你可以多说说，为什么你会这样看吗？
```

或：

```text
你刚才提到的这个点，我想再听你展开一点：它为什么重要？
```

## 8. 示例对比

### 8.1 阶段主问题

当前：

```text
你认为当前最核心的决策问题是什么？你会怎样界定这个问题？
```

建议：

```text
如果你是项目负责人，看到这个情况后，你最想先弄清楚的问题是什么？
```

### 8.2 用户回答较短

用户：

```text
我觉得还是要上线。
```

不建议追问：

```text
你觉得上线时间和产品稳定性之间是什么关系？
```

建议追问：

```text
你说想按时上线，我想多听听你的考虑：为什么上线这件事在你这里比较重要？
```

### 8.3 用户提到某个关键词

用户：

```text
我觉得市场窗口很重要，不能错过。
```

建议追问：

```text
你刚才提到市场窗口很重要，可以多说说为什么它在这个决策里这么关键吗？
```

### 8.4 用户表达抽象

用户：

```text
我觉得风险要控制好。
```

建议追问：

```text
你说到要控制风险，可以具体讲讲你最担心的是哪一类风险吗？
```

## 9. 分阶段落地计划

### 9.1 第一阶段：配置与 Prompt 调整

目标：不改数据库结构，先修正提问机制。

任务：

1. 修改 `scenario_product_48h.yaml` 中各阶段 `main_question`，确保每个问题只问一个点；
2. 修改各阶段 `StageInterventionRule` 的 `strategy_direction`，从收束型改为开放访谈型；
3. 修改 `sample_question`，减少二元取舍、标准答案提示和格式要求；
4. 在 `question_generation_constraints_json` 中加入非指令性访谈约束；
5. 更新 FollowupAgent prompt，要求每轮只问一个问题、优先使用用户原话。

验收标准：

- 用户可见问题中不再出现复合问题；
- 追问不主动引入用户未提到的二元框架；
- 用户更容易自然展开回答。

### 9.2 第二阶段：追问质量审计

目标：让系统能自动发现追问是否过度收束。

任务：

1. 在 FollowupOutput 中记录 `followup_intent`、`user_freedom_level`、`visible_question_count`、`introduced_assumptions`、`quality_flags`；
2. 将这些字段保存到 `AgentTrace.output_json`；
3. 增加轻量质量检查逻辑；
4. 后台管理系统后续可展示追问质量指标。

验收标准：

- 每轮追问都能在 `AgentTrace` 中看到追问意图和质量标记；
- 能判断某次追问是否违反“单问题、用户原话、无二元框架、无标准答案提示”原则。

### 9.3 第三阶段：后台配置支持

目标：让心理组能通过后台调整访谈策略。

任务：

1. 后台追问规则编辑页展示 `question_generation_constraints_json`；
2. 支持配置 `user_freedom_level`、`allowed_probe_modes`、`forbidden_framing`；
3. 支持查看每条追问规则的实际使用效果；
4. 后台数据分析页增加追问质量统计。

验收标准：

- 心理组可以调整追问开放度；
- 管理员可以查看某类规则是否经常产生限制性追问；
- 后续迭代不需要直接改代码。

## 10. 与现有数据模型的关系

| 机制需求 | 对应数据模型 | 是否需要新增字段 |
| --- | --- | --- |
| 阶段第一问单问题化 | `scenario_stage.main_question` | 否 |
| 开放式追问策略 | `stage_intervention_rule.strategy_direction` | 否 |
| 追问参考问法 | `stage_intervention_rule.sample_question` | 否 |
| 追问边界与开放度 | `stage_intervention_rule.question_generation_constraints_json` | 否 |
| 用户可见文本 | `dialogue_turn.content` | 否 |
| 追问来源规则 | `dialogue_turn.intervention_rule_id` | 否 |
| Agent 决策过程 | `agent_trace.output_json` | 否 |
| 追问质量审计 | `agent_trace.output_json.quality_flags` | 否 |
| 后续问题节点规范化 | 预留 `stage_question_item` | V2 可选 |

## 11. 结论

本次优化的关键不是让 AI 说得更像心理咨询师，而是让它更像一位合格的数字面试官。

正确方向应是：

> 用户端降低限制，后台端增强结构。

也就是：

- 用户看到的是一个开放、自然、低压的问题；
- AI 顺着用户原话继续访谈；
- 系统后台用六维能力模型、rubric 和 AgentTrace 抽取证据；
- 每轮追问都能解释为什么问、服务哪个维度、缺什么证据、有没有过度引导。

第一版应优先通过配置、Prompt 和 AgentTrace 输出契约完成落地，不急于新增数据库表。等访谈流程稳定后，再考虑将阶段问题节点进一步规范化为独立表。
