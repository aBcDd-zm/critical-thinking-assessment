# Demo 2.0 需求分析：数字面试官式审辩式思维测评

## 1. 背景与核心判断

当前 Demo 已经跑通“情境呈现、用户回答、AI 追问、阶段推进、评分报告、后台配置与数据看板”的基本闭环。指导老师这次反馈的重点，不是简单增加一个语音按钮，也不是把页面做得更花，而是要求系统的测评交互形态发生升级：

1. 用户不应感觉自己在做网页问答，而应感觉自己正在和一位数字面试官交流；
2. 测评过程要鼓励用户多讲，尽量暴露真实思考过程；
3. 情境提问和追问策略要更开放，不要过早把用户引向固定答案；
4. 心理组需要提供更细的访谈策略、追问规则和证据充分性判断标准；
5. 后台管理端需要更直观地分析用户行为、访谈过程、证据覆盖和 Agent 运行质量。

Demo 2.0 的核心定位是：从“对话式测评 Demo”升级为“数字面试官式动态访谈测评 Demo”。

这件事的关键不是“数字人外观”，而是“访谈式证据采集”。数字人、语音、动画是体验层；真正决定测评质量的是：系统能否让用户讲出更多决策理由、权衡过程、证据判断、假设前提和动态调整思路。

## 2. Demo 2.0 目标

| 方向 | 当前状态 | Demo 2.0 目标 |
| --- | --- | --- |
| 前台交互 | 文字聊天为主，仍像一问一答 | 数字面试官式访谈体验，支持语音入口和面试官状态反馈 |
| 情境呈现 | 以阶段问题为主 | 面试官用自然语言渐进呈现情境，减少考试感 |
| 追问策略 | 偏补缺口、推进流程 | 偏开放深挖，引导用户多讲理由、过程、假设和权衡 |
| 心理配置 | 已有六维能力、评分锚点、情境阶段、追问规则 | 增加访谈策略、开放式追问、证据充分性和无效表达规则 |
| 数据采集 | 已保存对话、AgentTrace、评分、报告、反馈 | 增加表达充分性、追问目标、追问效果、语音输入行为等数据 |
| 后台分析 | 已有运行概览、阶段热度、反馈均值 | 增加图表化分析、单会话复盘、证据覆盖、追问效果和流程质量看板 |

## 3. 需求边界

### 3.1 Demo 2.0 必须解决

1. 前台主流程呈现为“数字面试官访谈”，用户看到的是面试官在和自己聊；
2. 主问题和追问话术改成开放式访谈风格；
3. 用户短回答时，系统能自然鼓励用户多讲；
4. 用户长回答时，系统能围绕用户原话继续深挖；
5. 心理组的访谈规则能进入后台配置或 seed，不写死在代码里；
6. 后台能用图表展示用户表达、阶段推进、证据覆盖、追问效果和 Agent 运行质量；
7. 文字输入必须保留，语音失败不能影响测评主流程。

### 3.2 Demo 2.0 暂不强求

1. 不强求真实 3D 数字人口型同步；
2. 不强求实时语音打断；
3. 不强求全程只能语音；
4. 不强求多模态表情识别；
5. 不强求完全自动优化追问策略。

建议采用“先做数字面试官体验和访谈机制，再逐步接入语音和更真实数字人”的路线。

## 4. 业务流程调整

### 4.1 当前流程

```text
用户输入昵称
-> 系统创建测评会话
-> AI 呈现阶段问题
-> 用户文字回答
-> AI 根据阶段目标和追问规则追问
-> 达到条件后进入下一阶段
-> 完成测评
-> 生成报告
-> 用户提交反馈
-> 后台查看数据
```

当前流程可以跑通，但用户容易把它理解为“答题”。如果用户回答偏短，系统收集到的行为证据会不足。

### 4.2 Demo 2.0 推荐流程

```text
数字面试官建立访谈关系
-> 轻量介绍本次交流方式
-> 渐进呈现管理决策情境
-> 提出开放式访谈问题
-> 用户用语音或文字自由表达
-> 系统保存原始回答、转写文本和行为数据
-> AI 判断表达充分性与证据覆盖
-> AI 用开放式追问引导用户继续讲
-> 必要时释放动态信息或挑战问题
-> 收集到足够证据后自然过渡到下一主题
-> 生成六维评分与结构化报告
-> 用户提交体验反馈
-> 后台分析访谈质量、用户行为和测评流程
```

### 4.3 核心变化

| 变化点 | 旧思路 | Demo 2.0 思路 |
| --- | --- | --- |
| AI 身份 | 测评主持人 | 数字面试官 |
| 用户感受 | 回答系统问题 | 和面试官交流自己的判断 |
| 情境呈现 | 一次性给出问题 | 渐进讲述，像真实谈话 |
| 追问目的 | 补缺口、推进阶段 | 引导用户展开，收集更多证据 |
| 动态信息 | 尽快释放新材料 | 用户已有初步表达后再释放 |
| 后台价值 | 看数量和配置 | 看访谈质量、证据质量和流程问题 |

## 5. 核心功能需求

### FR-01 数字面试官式主交互页

目标：让用户进入测评后，第一感受是“我在和一位数字面试官交流”，而不是“我在填网页题”。

系统需求：

1. 前台测评页以面试官区域和对话区域为核心；
2. 面试官区域展示头像、状态、当前阶段、语音播放或思考状态；
3. 对话区域只展示必要内容，不堆积后台指标；
4. 用户输入区支持文字输入，并预留语音录制入口；
5. 面试官提问要有自然过渡，减少“第 N 题”“请作答”这类考试感表达；
6. 阶段切换时用访谈式过渡，例如“我理解你的想法了，我们再换一个角度聊聊”。

预期效果：

用户更愿意自然表达，前台体验更接近访谈或轻面试，演示时也更容易体现系统特色。

### FR-02 语音优先的回答入口

目标：降低用户表达负担，让用户更容易说出长回答。

系统需求：

1. 页面提供麦克风按钮，支持用户语音输入；
2. 语音转写后展示转写文本，允许用户确认或修改；
3. 文字输入作为兜底能力保留；
4. 每轮回答需要记录输入方式：`text`、`voice` 或 `mixed`；
5. 如接入语音播报，AI 问题可以同步播放语音；
6. 语音能力失败时，不中断文字测评流程。

实现建议：

1. Demo 2.0 可以先用浏览器 Web Speech API 或轻量语音服务完成语音输入原型；
2. 音频是否保存需要谨慎，默认建议先只保存转写文本；
3. 如需要保存音频，必须在测评前告知用户。

预期效果：

用户回答长度更长、表达更自然，后台可以分析语音使用率和回答时长。

### FR-03 访谈式情境提问配置

目标：把原来的“阶段题目”改成“访谈主题”，由配置引导 AI 面试官自然提问。

现有承接：

系统已有 `ScenarioStage`，包含 `stage_goal`、`context`、`main_question`、`context_generation_mode`、`context_ai_weight`、`context_generation_constraints_json` 等字段，已经可以支持配置与 AI 生成比重控制。

调整需求：

1. 心理组需要把每个阶段的 `main_question` 改成开放式访谈问题；
2. `stage_goal` 不只写“测什么”，还要写“希望用户讲出什么”；
3. `context_generation_constraints_json` 中应写清楚：哪些情境事实不能改，哪些表达可以由 AI 面试官自然转述；
4. 每个阶段需要增加“访谈引导目标”，例如让用户讲出理由、证据、假设、顾虑、备选方案；
5. AI 不应一次性把所有背景信息抛给用户，允许分段呈现。

示例方向：

| 阶段 | 原提问倾向 | Demo 2.0 访谈式提问倾向 |
| --- | --- | --- |
| 问题界定 | 你认为核心问题是什么 | 你先按自己的理解说说，这件事最让你卡住的地方是什么 |
| 证据评估 | 你需要哪些信息 | 如果你真的负责这件事，你会先去确认哪些情况，为什么 |
| 多元视角 | 你考虑哪些角色 | 你觉得不同团队或利益相关方分别会担心什么 |
| 推理论证 | 你的理由是什么 | 你可以把自己的判断过程讲出来，我想听听你是怎么推到这个结论的 |
| 动态调整 | 新信息下如何调整 | 如果现在补充一个变化，你会怎么修正刚才的判断 |
| 整合决策 | 最终方案是什么 | 如果接下来 24 到 48 小时由你拍板，你会怎么安排行动 |

预期效果：

用户回答不再只是给结论，而是更容易说出完整思考过程。

### FR-04 开放式追问与表达充分性判断

目标：追问从“收缩问题范围”改为“引导用户多讲”，让系统收集更充分的评分证据。

现有承接：

系统已有 `StageInterventionRule`，包含 `rule_type`、`trigger_condition`、`strategy_direction`、`sample_question`、`question_generation_mode`、`question_ai_weight`、`question_generation_constraints_json`、`fallback_question`、`max_use_count` 等字段。它可以继续作为追问策略配置的核心表。

新增追问类型建议：

| rule_type | 目标 | 示例方向 |
| --- | --- | --- |
| `elaboration_probe` | 鼓励用户展开更多细节 | 你可以再展开讲讲这个判断背后的考虑 |
| `reasoning_probe` | 挖掘推理过程 | 你是怎么从这些信息推到这个结论的 |
| `assumption_probe` | 暴露前提假设 | 这个判断成立，需要哪些前提是真的 |
| `uncertainty_probe` | 观察不确定性意识 | 这里你最不确定的地方是什么 |
| `tradeoff_probe` | 观察权衡能力 | 如果两个目标冲突，你会怎么取舍 |
| `stakeholder_probe` | 观察多元视角 | 不同团队可能会分别担心什么 |
| `action_probe` | 观察行动落地 | 如果明天就执行，你第一步会做什么 |
| `reflection_probe` | 观察自我修正 | 你觉得刚才的方案里最可能出问题的是哪里 |

追问策略要求：

1. 优先围绕用户原话继续追问；
2. 用户回答短时，先鼓励展开，不急着释放新信息；
3. 用户回答泛时，引导其举例、说明原因或补充判断过程；
4. 用户表达较充分后，再进入挑战、动态信息或阶段推进；
5. 追问不能泄露评分标准；
6. 追问不能强行暗示标准答案；
7. 每次追问都要记录追问目标，便于后台分析追问是否有效。

预期效果：

系统能够从用户自然表达中获取更多行为证据，评分和报告更有依据。

### FR-05 动态信息释放策略调整

目标：动态信息不再作为早期“加题材料”，而是作为访谈中后段观察用户动态调整能力的工具。

系统需求：

1. 用户尚未充分表达原始判断前，不优先释放动态信息；
2. 用户已形成初步判断或方案后，再释放动态信息；
3. 释放动态信息后，追问重点是“这个变化如何影响你的判断”；
4. 同一条动态信息在同一 session 中不重复释放；
5. 用户实际看到的动态信息必须和 `DialogueTurn.dynamic_info_id`、`AgentTrace.selected_dynamic_info_id` 对得上。

预期效果：

动态信息更像真实访谈中的补充事实，能够更好观察用户的修正能力和动态决策能力。

### FR-06 后台数据看板增强

目标：让后台不仅能看系统有没有运行，还能看测评过程质量如何。

现有承接：

后台已有：

1. `/admin/dashboard/summary`：配置资产统计；
2. `/admin/dashboard/analytics`：会话数量、完成率、平均耗时、平均轮次、Agent 调用、报告、评分证据、用户反馈、阶段进度等；
3. `DashboardView.vue`：已有运行概览、会话状态、最近测评记录、阶段观察热度、用户反馈与配置资产。

Demo 2.0 增强需求：

| 图表 | 数据来源 | 价值 |
| --- | --- | --- |
| 测评漏斗图 | `assessment_session.status`、报告、反馈 | 看开始、完成、报告、反馈转化 |
| 阶段耗时柱状图 | `DialogueTurn.created_at`、`ScenarioStage` | 看哪个阶段拖慢流程 |
| 回答长度分布图 | `DialogueTurn.content`、后续 `word_count` | 看用户是否愿意多讲 |
| 语音使用率 | 后续 `input_mode` | 看语音交互是否被使用 |
| 证据覆盖雷达图 | `score_result`、`score_evidence` | 看六维证据是否均衡 |
| 追问类型效果图 | `AgentTrace.output_json`、`StageInterventionRule.rule_type` | 看哪类追问更能带来有效证据 |
| Agent 耗时图 | `AgentTrace.duration_ms` | 看模型调用性能 |
| fallback 比例图 | `AgentTrace.status`、`warnings` | 看稳定性 |
| 用户反馈热力图 | `session_feedback` | 看自然度、疲劳感、可信度 |

预期效果：

后台能支持管理员复盘“用户为什么答得少”“哪个阶段证据不足”“哪类追问有效”“模型哪里慢或失败”。

### FR-07 单会话复盘页

目标：让管理员能打开某一次测评，看到完整访谈过程和评分证据链。

页面需求：

1. 展示用户完整对话时间线；
2. 每轮展示输入方式、回答字数、回答时长；
3. 展示 AI 每次追问的 `rule_type`、`probe_goal`、选中规则、动态信息；
4. 展示每阶段证据覆盖情况；
5. 展示评分证据句对应哪一轮用户回答；
6. 展示最终报告与用户反馈；
7. 标记低信息回答、兜底追问、fallback、超时调用等异常。

预期效果：

这个页面是 Demo 2.0 的重要展示点。它能证明系统不是只会聊天，而是在做过程性、可追溯的测评。

### FR-08 心理配置中心增强

目标：让心理组可以把访谈规则、追问策略和评分证据规则持续迭代到系统里。

配置需求：

1. 每个阶段可配置访谈目标；
2. 每个阶段可配置开放式主问题；
3. 每个阶段可配置鼓励展开式追问；
4. 每个阶段可配置低信息回答兜底问题；
5. 每个阶段可配置不推荐问法；
6. 每个维度可配置有效证据、弱证据、无效证据；
7. 每条追问规则可配置目标维度和使用上限；
8. 配置变更应能通过 seed 或后台导出。

预期效果：

心理组不需要改代码，也能持续优化“怎么问、问什么、怎么判断证据是否充分”。

## 6. 心理组交付物需求

为了支撑 Demo 2.0，心理组建议产出以下材料：

| 交付物 | 说明 | 落地位置 |
| --- | --- | --- |
| 六阶段访谈目标 | 每阶段希望用户讲出什么 | `ScenarioStage.stage_goal` |
| 开放式主问题 | 每阶段面试官第一问 | `ScenarioStage.main_question` |
| 访谈引导语 | 降低紧张感、鼓励真实表达 | Prompt / HostAgent 配置 |
| 开放式追问策略 | 引导用户展开理由、证据、假设、权衡 | `StageInterventionRule` |
| 低信息兜底问题 | 用户答“无、不知道”时怎么自然追问 | `fallback_question` |
| 不推荐问法 | 避免诱导、限制、暗示标准答案 | `question_generation_constraints_json` |
| 表达充分性标准 | 何时认为证据够了，可以推进 | `exit_criteria_json` / Agent 输出 |
| 有效/无效证据规则 | 什么表达可评分，什么表达不能高分 | `RubricDimension` / `RubricAnchor` |
| 动态信息释放规则 | 什么时候给新信息最合适 | `StageDynamicInfo.trigger_condition` |
| 追问效果判断 | 追问后是否收集到了新增证据 | AgentTrace / 后台分析 |

心理组材料的写法建议不要只写理论，应尽量写成“AI 可以使用的配置”。例如：

```text
阶段：证据评估
访谈目标：让用户说明自己会优先确认哪些事实、数据来源和可靠性判断。
鼓励展开：你可以按真实处理事情的顺序说，不需要一下子给出标准答案。
低信息判断：只说“看数据”但不说明看什么数据、数据来自哪里、为什么重要。
开放追问：你刚才提到要看数据，你会先看哪两三类数据？这些数据分别能帮你判断什么？
避免问法：不要直接问“你是否会看用户反馈、测试数据和市场窗口”，因为这会给出提示。
```

## 7. Agent 调整需求

### 7.1 HostAgent

定位：从“流程主持人”升级为“数字面试官”。

新增要求：

1. 开场降低用户紧张感；
2. 提问方式更像访谈，不像题目；
3. 能把长情境拆成短段讲述；
4. 阶段切换时自然过渡；
5. 输出中保留 `generation_mode`、`ai_generation_weight` 和 reason，便于后台追踪。

### 7.2 FollowupAgent

定位：从“缺口追问器”升级为“访谈深挖器”。

新增要求：

1. 优先根据用户原话追问；
2. 输出新增 `probe_goal`，说明本次追问目标；
3. 输出新增 `evidence_gap_before`，说明追问前证据缺口；
4. 输出新增 `expected_user_expansion`，说明希望用户展开哪些内容；
5. 低信息回答时使用阶段化兜底；
6. 动态信息不重复释放；
7. 动态信息释放时，用户可见文本必须包含该信息。

### 7.3 ScoringAgent

定位：从“最终打分”升级为“基于访谈证据的评分解释”。

新增要求：

1. 能处理更长、更口语化的回答；
2. 能区分“说得多但无效”和“表达具体且可评分”；
3. 每个维度评分必须引用用户原话；
4. 对低信息回答标记低置信度或证据不足；
5. 能汇总每个阶段的证据覆盖情况。

### 7.4 ReportAgent

定位：从“结果报告生成器”升级为“过程性反馈生成器”。

新增要求：

1. 报告说明用户在哪些访谈片段中体现了能力；
2. 能解释某些维度低分是证据不足还是表现较弱；
3. 可展示“追问前后表达变化”；
4. 报告语言克制、专业，不做医学诊断。

## 10. 前端体验需求

### 10.1 用户测评端

页面结构建议：

1. 左侧或顶部：数字面试官区域；
2. 中间：当前访谈内容和用户回答；
3. 底部：语音按钮、文字输入、确认提交；
4. 辅助位置：轻量阶段进度，不展示复杂指标。

面试官状态：

| 状态 | 用户表现 |
| --- | --- |
| `speaking` | 面试官正在讲述，字幕流式出现 |
| `listening` | 麦克风可用，鼓励用户说出想法 |
| `thinking` | AI 分析中，展示轻量思考状态 |
| `probing` | 面试官准备继续深挖 |
| `transitioning` | 阶段自然过渡 |

### 10.2 后台管理端

后台不追求花哨，而要信息直观：

1. 首页优先展示关键指标和趋势图；
2. 图表要能回答“流程是否健康”“证据是否充分”“追问是否有效”；
3. 单会话复盘页要适合演示；
4. 配置页继续保持可编辑、可维护。

## 12. Demo 2.0 验收标准

### 12.1 用户端验收

1. 用户进入测评后，能明显感受到数字面试官在引导访谈；
2. 主问题不再像考试题，而是开放式交流；
3. 用户短回答时，AI 能鼓励其继续展开；
4. 用户长回答时，AI 能抓住用户原话继续深挖；
5. 文字输入可完成完整流程；
6. 如接入语音，语音失败时文字流程仍可用。

### 12.2 Agent 验收

1. HostAgent 提问自然，有阶段过渡；
2. FollowupAgent 输出包含追问目标；
3. FollowupAgent 不过早释放动态信息；
4. 动态信息不重复释放；
5. ScoringAgent 能处理长文本和低信息回答；
6. ReportAgent 能引用访谈片段解释评分。

### 12.3 后台验收

1. 看板能展示测评漏斗；
2. 看板能展示阶段耗时；
3. 看板能展示用户回答长度或时长；
4. 看板能展示六维证据覆盖；
5. 看板能展示 Agent 成功率、耗时、fallback；
6. 单会话复盘页能看到对话、追问策略、证据、报告和反馈。

## 13. 初步结论

Demo 2.0 的方向是对的，而且和当前系统架构兼容。现有数据库已经有情境、阶段、追问规则、动态信息、AgentTrace、DialogueTurn、评分证据和反馈这些基础，能够承接“数字面试官式访谈”的主体升级。

下一步最重要的不是立刻追求复杂数字人，而是先把三件事做好：

1. 前台看起来、用起来像数字面试官访谈；
2. 心理组把开放式追问和证据充分性规则配置出来；
3. 后台能用图表和会话复盘证明系统真的在收集、分析和解释用户行为。

这三件事完成后，Demo 2.0 就能明显区别于普通问卷、普通聊天机器人和简单大模型问答。
