## 1. 目标与边界

追问的唯一目的，是在统一情境和有限时间内补充当前评分最需要的行为证据，或检验用户已有论证的稳定性。追问不是为了延长聊天，也不是为了帮助用户说出“正确答案”。

人本主义访谈式表达是中性的交互增强层：接住用户已经表达的内容、准确复述、降低被审问感，再围绕一个证据缺口提问。它不是心理咨询，不测量共情、情绪或人格，也不得进行诊断、治疗建议或情绪分析。

## 2. 统一测评结构

### 2.1 三类系统话语

| 类型 | 定义 | 是否计入追问上限 | 是否作为用户证据 |
| --- | --- | ---: | ---: |
| 固定核心问题 | 六阶段预先配置的主问题，所有用户原则上都接触 | 否 | 问题本身不计；用户回答可计 |
| 动态信息干预 | 从预先批准的信息池中释放一条与用户路径相关的新信息，并要求回应 | 是 | 系统信息不计；用户回应可计 |
| 澄清/挑战追问 | 针对回答中的一个明确证据缺口、逻辑漏洞或矛盾发问 | 是 | 问题本身不计；用户回应可计 |

同一阶段最多出现一次可计数干预：动态信息干预与澄清/挑战追问二选一，不得先释放动态信息后再连续追加两次追问。

### 2.2 轮次控制

- 每阶段最多 1 次可计数干预；
- 整场最多 4 次可计数干预；
- 六个固定核心问题不计入上限；
- 达到整场上限后，即使仍有证据缺口，也应继续阶段流程并在评分中标记证据不足；
- 不得因为回答字数短而自动追问；短回答若已提供充分证据，可以直接进入下一阶段；
- 长回答若缺少目标维度证据，仍可触发追问；
- 预计总测评时长不超过 30 分钟。

当前 `scenario_product_48h.yaml` 中各阶段 `max_followups: 2`、第五阶段 `max_followups: 3` 属于 Agent 测试设置，正式版应改为阶段上限 1，并由会话层增加 `session_followup_cap: 4`。

## 3. 追问决策流程

```text
用户回答
→ 数据质量检查
→ 当前阶段主测维度证据识别
→ 判断是否达到最低可评分标准
→ 识别最高优先级的一个证据缺口
→ 选择追问类型或动态信息
→ 生成候选问题
→ 质量与泄露检查
→ 发出一条追问
→ 抽取新增证据并记录追问增益
→ 推进阶段
```

### 3.1 不应追问的情况

- 当前回答已达到该阶段主测维度的基本可评分标准；
- 追问只能补充辅测维度，而主测维度已经充分；
- 本阶段或整场上限已达到；
- 用户明确选择退出；
- 出现技术错误，应走错误恢复流程而不是能力追问；
- 问题会提示标准答案、特定方案或 Rubric 内容；
- 追问与当前情境无关，或只是为了让对话更自然。

## 4. 触发条件与操作化规则

| 触发代码 | 可观察条件 | 追问目标 | 推荐类型 | 不应使用的做法 |
| --- | --- | --- | --- | --- |
| `off_topic_or_unusable` | 回答与情境无关、乱码、复制无关内容，无法形成证据 | 恢复有效作答机会 | 简短重述任务 | 暗示这是低能力表现 |
| `conclusion_only` | 只有结论或选择，没有理由 | 补充证据和理由链 | 索证/澄清 | 直接替用户列出理由 |
| `vague_problem` | 复述背景或只说“要权衡”，未形成核心问题 | 明确问题、边界和约束 | 问题界定澄清 | 把“灰度上线”作为暗示答案 |
| `unspecified_evidence` | 只说“看数据”，未说明数据、来源或质量 | 补充来源、可靠性和核实方式 | 证据追问 | 给出完整指标清单让用户照抄 |
| `single_metric` | 仅凭数量、失败率或某部门意见判断 | 检验单一证据局限 | 反证/交叉验证 | 直接否定用户所用指标 |
| `reasoning_gap` | 前提、证据和结论之间存在明显跳跃 | 展开理由链和关键假设 | 推理澄清 | 替用户补全逻辑链 |
| `single_perspective` | 只考虑一个部门或角色 | 补充被忽略的相关方及冲突 | 视角转换 | 要求用户机械列出固定角色 |
| `unexamined_assumption` | 方案依赖未说明的关键假设 | 检验假设不成立时的变化 | 轻度挑战 | 告知用户“你的推理是错的” |
| `new_info_unaddressed` | 新信息出现后仍机械重复原方案 | 观察动态调整及其理由 | 动态更新 | 强迫用户必须改变结论 |
| `vague_action_plan` | 只有原则，缺少步骤、责任、阈值或兜底 | 形成可执行方案 | 行动具体化 | 要求写完整商业计划书 |
| `internal_contradiction` | 同一会话中出现实质性矛盾且未解释 | 澄清判断变化或条件差异 | 一致性澄清 | 用指责性语气抓错 |

## 5. 优先级与选择规则

同一回答可能同时存在多个缺口。FollowupAgent 每次只能选择一个，优先级如下：

1. 无法形成任何有效回答的数据质量问题；
2. 当前阶段主测维度完全缺证据；
3. 当前阶段主测维度的关键逻辑漏洞或前后矛盾；
4. 预先配置且与当前回答相关的动态信息；
5. 主测维度已有基本证据但存在一个可显著提高可判定性的缺口；
6. 辅测维度缺口原则上不单独触发追问。

若两个候选问题优先级相同，选择：

- 更贴近用户原话的；
- 更少暗示答案的；
- 认知负担更低的；
- 更可能产生可区分 2/3 或 4/5 等级证据的；
- 已使用次数更少的规则。

## 6. 人本主义表达层

推荐结构：

```text
接住已有表达（可选）
→ 中性复述用户已明确说出的内容
→ 安全提示（仅必要时）
→ 围绕一个证据缺口提问
```

### 6.1 合格示例

> 你目前更倾向于控制核心功能风险。为了更准确理解你的判断，你会优先核实哪些数据，以及这些数据分别来自哪里？

> 你已经提到市场与研发的不同诉求。如果换到用户或运营视角，他们最可能担心什么？

### 6.2 不合格示例

> 你是不是忽略了用户？

问题：指责性强，并泄露评分缺口。

> 正确做法应该是灰度上线，你为什么没有考虑？

问题：暗示标准答案并改变被试原始判断。

> 你很焦虑，所以无法理性分析吗？

问题：越界进行心理状态推断。

### 6.3 表达限制

- “我理解”“听起来”后只能复述用户明确表达的内容，不得增加模型推断；
- 不使用“正确”“错误”“成熟”“优秀”“不理性”等评价性词语；
- 不连续问多个子问题；确需询问来源与验证方式时，应保持一个中心目标；
- 不把维度名称、评分等级或高分锚点直接告诉用户；
- 不夸奖具体审辩行为，以免向后续回答提供得分线索。

## 7. 追问生成后的质量筛选

候选追问必须同时满足：

1. 与当前阶段和用户原话直接相关；
2. 绑定一个 `trigger_code` 和一个主目标维度；
3. 只处理一个主要证据缺口；
4. 不包含 Rubric、高分特征或推荐方案；
5. 不引入配置外的新事实；
6. 不重复此前已问过的问题；
7. 中文清晰，通常控制在 20–70 字；
8. 不进行人格、情绪或临床推断；
9. 有对应 `fallback_question`；
10. 未超过阶段和会话上限。

任一项不通过时，使用已批准的 `fallback_question`；不得继续让模型自由重写多次造成延迟和漂移。

## 8. 行为证据定义

行为证据必须来自用户实际输入，不得来自：

- 情境材料；
- HostAgent 或 FollowupAgent 的问题；
- 报告生成文本；
- 模型对用户的概括；
- 专家为用户补写的解释。

证据应采用“最小充分片段”原则：截取能够独立说明目标行为的最短连续语段，同时保留字符起止位置，避免只摘取失去上下文的单个词。

## 9. 证据分类

### 9.1 有效性类型

| `validity` | 含义 | 示例 | 处理 |
| --- | --- | --- | --- |
| `valid` | 直接表现目标行为 | “我会将日志、客服记录和灰度数据交叉核实” | 进入评分 |
| `weak` | 相关但笼统或不完整 | “我要多看数据” | 作为弱证据，不单独支撑高分 |
| `invalid_restatement` | 复述题干或情境信息 | “现在有市场和研发冲突” | 不进入评分 |
| `invalid_attitude` | 只有态度、价值表态或自我评价 | “我做事一向很谨慎” | 不进入评分 |
| `invalid_authority` | 仅以权威或部门意见代替判断 | “老板要求上线，所以就上线” | 不进入高水平证据，可成为低分行为证据 |
| `invalid_unsupported` | 无依据结论 | “这个风险肯定没问题” | 不进入高水平证据，可成为低分行为证据 |
| `invalid_prompt_echo` | 复制系统问题中提供的内容，没有自主展开 | 原样复制追问中的指标或角色 | 不作为新增证据 |
| `unusable` | 乱码、无关文本、技术截断 | 随机字符 | 标记数据质量问题 |

### 9.2 证据强度

| `strength` | 定义 | 使用规则 |
| ---: | --- | --- |
| 0 | 无效或不可用 | 不支撑分数 |
| 1 | 弱相关、单一要素或模糊表达 | 可支持 2 分或补充 3 分 |
| 2 | 直接、清晰表现维度核心行为 | 可支持 3–4 分，仍需匹配完整锚点 |
| 3 | 连接多个关键要素，含边界、自我检验或可执行闭环 | 可作为 4–5 分候选，不自动等于 5 分 |

强度不是分数。最终分数仍由完整 BARS 匹配决定。

## 10. 证据结构化字段

每条证据至少包含：

```json
{
  "evidence_id": "uuid",
  "session_id": "uuid",
  "scenario_code": "product_launch_48h",
  "scenario_version": "assessment_v1",
  "stage_code": "s2_evidence_verification",
  "turn_id": "uuid",
  "turn_index": 4,
  "source": "main_answer | adaptive_followup",
  "quote": "用户原话最小充分片段",
  "start_char": 12,
  "end_char": 48,
  "dimension_key": "evidence_evaluation",
  "validity": "valid",
  "strength": 2,
  "novelty": "new | repeated | elaborated",
  "trigger_code": "unspecified_evidence",
  "rationale": "该句说明了证据来源与交叉验证方式",
  "extractor_type": "expert | llm | rule",
  "extractor_version": "evidence_v1"
}
```

同一原话可标注多个维度，但每个维度应生成独立证据记录和独立理由。

## 11. 追问增益记录

系统不得只用“追问后文字变长”证明追问有效。每次追问需记录：

- `evidence_count_before` 与 `evidence_count_after`；
- 主测维度是否获得新增有效证据；
- 新证据是 `new`、`elaborated` 还是 `repeated`；
- 追问前后证据充分状态；
- 追问前后评分置信度；
- 追问耗时；
- 用户是否出现重复、疲劳或退出。

建议核心指标：

```text
有效追问率 = 产生至少一条新有效证据的追问数 / 总追问数
证据补全率 = 从证据不足转为可评分的目标维度数 / 被追问的证据不足维度数
```

追问增益研究需要设置固定追问或无自适应追问对照，不能仅凭同一用户追问前后文字增加作因果结论。

## 12. FollowupAgent 输出规范

```json
{
  "should_followup": true,
  "selected_rule_code": "clarify_evidence_source",
  "trigger_code": "unspecified_evidence",
  "target_dimension": "evidence_evaluation",
  "question_type": "clarify",
  "question": "你提到需要看数据。你会优先核实哪些数据，这些数据分别来自哪里？",
  "reason": "当前回答未说明证据来源和可靠性",
  "evidence_gap": "source_and_reliability_missing",
  "stage_followups_used": 0,
  "session_followups_used": 1,
  "quality_checks": {
    "on_topic": true,
    "single_gap": true,
    "non_leading": true,
    "no_construct_leakage": true,
    "within_limit": true
  },
  "prompt_version": "followup_v1"
}
```

当 `should_followup=false` 时，应返回不追问原因，如 `evidence_sufficient`、`stage_cap_reached`、`session_cap_reached`、`user_exit` 或 `technical_recovery_required`。

## 13. 验收测试

正式接入前至少通过以下案例：

1. 短但证据充分的回答：不追问；
2. 长但只有套话的回答：追问一个核心缺口；
3. 同时缺证据和多元视角：只选择当前主测维度；
4. 已达到整场 4 次：不再追问并标记证据不足；
5. 动态信息已释放：同阶段不再追加第二个干预；
6. 用户选择特定方案但理由充分：不因方案偏好追问；
7. 问题候选包含“灰度上线”等答案暗示：质量检查失败并使用兜底问题；
8. 用户改变方案且说明新证据：识别动态调整证据，不机械追问“为什么改变”；
9. 用户复制追问内容：标记 `invalid_prompt_echo`；
10. 乱码或技术截断：走数据质量恢复，不记低能力分。

## 14. 版本与复核

- 每次修改记录 `followup_prompt_version`、规则版本、修改原因和测试结果；
- 正式采集开始后不得静默修改追问策略；
- 预测试需抽取追问记录由人工检查相关性、引导性、重复性和新增证据；
- 低质量追问样本必须进入反例测试集；
- 正式报告中不展示内部触发代码，但后台必须保留完整追问依据。
